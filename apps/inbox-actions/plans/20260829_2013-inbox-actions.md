# Inbox Actions — build plan

**Date:** 2026-08-29
**Slug:** `inbox-actions`
**Request:** "an app that shows latest emails and whether they have action items attached to them"

---

## Context

Show the most recent messages from the mailbox, and for each one say whether it
carries **action items** — things somebody is being asked to do — rather than
just showing a subject line and leaving the reader to open every mail.

### Two constraints discovered while reading, both of which shape the design

**1. The Gmail connector is tenant-scoped and read-only.** `connectors/gmail/connector.json`
declares no `userScoped: true`, and `connectors/gmail/index.ts` opens with a
comment saying so in bold: an admin presses Connect once and *every user of
every app reads that single shared mailbox*. There is no per-user inbox
available, and the connector comment explicitly says it "must not be presented
as if it can."

So this app is **a shared-mailbox triage board**, not "your inbox". The UI says
which mailbox it is reading and never uses the word "your". This is a real
narrowing of the request and it is stated in the UI rather than papered over.

**2. There is no LLM available to app code.** No `anthropic`/`openai` connector
exists, and `context` exposes no model client. "Does this email have action
items" therefore has to be answered by a **deterministic extractor** over the
message body, not by a model.

That is a genuine limitation, so the app is built to be honest about it: every
detection **shows the sentence it matched**. The user is never asked to trust an
opaque badge — they see "2 action items" *and* the two lines, and can disagree at
a glance. A heuristic whose evidence is on screen is useful; one that hides its
reasoning is not.

## Decisions

| Decision | Choice | Why |
| --- | --- | --- |
| Data path | Declared `sync` → scoped tables → routes read the tables | `apps/AGENTS.md` invariant 26 and 21. A page must never wait on Gmail; hydrating 25 messages is ~26 upstream calls. |
| Detection | Deterministic rule extractor, run inside `upsert` | No LLM exists. It is pure local text work (sub-millisecond), so it needs no second enrichment phase or cadence. |
| Evidence | Store and display the matched sentence | The only honest way to ship a heuristic. See above. |
| Roles | None | The app has no mutations — nothing to gate. Declaring roles nobody enforces is noise. |
| MCP / telemetry / notifications | None | Not requested; each carries its own verification burden. |
| Connector on the read path | `?.configured` read only, never a call | Lets the page say "Gmail isn't set up yet" instead of showing an unexplained blank, and gives the smoke test its `UNCONFIGURED_TENANT` guard path on a cold install. |

### Why a declared `sync` and not a hand-rolled `jobs/` handler

Invariant 26 is explicit ("incremental sync is declared, not hand-rolled"), and
this is exactly the shape it covers: a date-windowed pull from a provider whose
pagination cursor expires between ticks. Gmail's search syntax takes
`after:`/`before:` as epoch seconds, which maps onto `SyncFetchArgs.{from,to}`
directly. The platform owns the watermark, the wall-clock budget, window
halving/relaxing and the empty-result guard; the cursor stays inside one run and
is never handed to app code, which is what makes the 19-day expired-cursor
outage unrepresentable here.

The one thing a declared sync does not give us is a read path that self-heals a
cold table. Accepted deliberately: on a cold install the page renders a
`no-data` empty state that names the cause ("the first sync hasn't run yet"),
which is a better first-run experience than a page that silently spends 30
seconds fanning out to Gmail on someone's first click.

### Detection rules (v1)

Run over the plain-text body (HTML stripped when there is no `text/plain` part),
sentence by sentence, skipping quoted replies and signature blocks:

| Kind | Matches | Example |
| --- | --- | --- |
| `request` | second-person ask — "can you", "could you", "please …", "would you mind" | "Could you review the draft?" |
| `assignment` | an explicit owner — "you need to", "you'll need to", "action required", "assigned to you" | "Action required: sign the form" |
| `question` | a direct question addressed to the reader | "Are we still on for Thursday?" |
| `deadline` | a date/time obligation — "by Friday", "due 3 Sept", "before EOD", "deadline" | "…by Friday at 5pm" |

A message's `action_count` is the number of distinct matched sentences (capped),
`has_deadline` is true when any match carried a deadline cue. Sentences from
quoted history (`>` prefixed, "On … wrote:" blocks) are excluded — otherwise
every reply in a long thread inherits the whole thread's asks.

The rule set lives in one client-safe module with a `DETECTOR_VERSION`, stamped
onto each row, so a future rules change is visible in the data rather than
silently mixed in.

```
  pages/
    Main.tsx                       client page: header, filter tabs in the URL, table

    action-summary.tsx             stat: N of the last M messages need action
```

### `migrations/001_messages.sql`

```sql
create table if not exists messages (
  id               text primary key,        -- Gmail message id
  thread_id        text not null,
  internal_date    timestamptz,             -- ordering key; null only if Gmail omitted it
  from_name        text,
  from_email       text,
  subject          text,
  snippet          text,
  is_unread        boolean not null default false,
  has_attachments  boolean not null default false,
  action_count     integer not null default 0,
  actions          jsonb   not null default '[]',  -- [{ kind, text }] — the matched sentences
  has_deadline     boolean not null default false,
  detector_version integer not null default 1,
  synced_at        timestamptz not null default now()
);
create index if not exists idx_messages_date    on messages (internal_date desc);
create index if not exists idx_messages_actions on messages (action_count);
```

`integer` for `action_count`, not `numeric` — per database.md, `numeric` comes
back from the driver as a **string** and would break `output: z.number()`.

### Routes

- `GET /messages` — `input { limit ≤ 100, filter: "all"|"needs-action"|"clear" }`,
  `output { messages[], syncedAt, gmailConfigured, mailbox }`. Reads the table
  only. Throws `AppError.unavailable()` when the table is empty **and** Gmail is
  unconfigured, so the guard path exists on a cold install.
- `GET /summary` — counts only (`{ total, needingAction, withDeadline, syncedAt }`).
  Separate from `/messages` so a stat widget doesn't pull 50 rows of bodies —
  the "fetch only what you render" rule from api-routes.md.

### Page

`pages/Main.tsx`, a client page using `useAppQuery` + `AsyncView` so loading,
refetch, error and empty are structural. Filter lives in the URL
(`?filter=needs-action`) per app-shell.md, with absent distinguished from
explicit. Rows are `DataTable`; each row expands to show its matched sentences.
Status uses `Badge`/`StatusDot` with a label — never colour alone.

Retention: `onDrained` prunes rows older than the retention window so the table
tracks "latest" rather than growing forever. The delete is bounded by
`internal_date` (delete-exactly-what-you-refetched applies in reverse here).

## What changed during the build (2026-08-31)

Four decisions moved once the code met the platform. Recorded here because the
plan is the design record, and a plan that quietly disagrees with the code is
worse than no plan.

### 1. `sync/` cannot import a connector — delegate to `lib/server/`

`eslint.config.mjs` allowlists `apps/**/api/**`, `services/**`, `mcp/**`,
`jobs/**` and `lib/server/**` for connector imports. **`apps/**/sync/**` is not
on that list**, even though a declared sync is server-only by construction and
runs with the same user-less `SystemAppContext` a job gets. The allowlist
predates the `sync` manifest field.

Fixed inside the app rather than by editing the platform config (that would be a
`docs/plans/` change, out of scope): all Gmail and detector work moved to
`lib/server/gmail-fetch.ts`, and `sync/messages.ts` is now wiring only. This is
the documented "server-only data builders they delegate to" shape, so it is a
better structure regardless. **Worth raising with the platform owners.**

### 2. An unconfigured connector must THROW, not return an empty page

The plan said return `{ items: [] }` to keep the admin page quiet. Reading
`src/lib/apps/sync.ts` showed why that is wrong:

```ts
const suspiciouslyEmpty = drained && items === 0 && state?.synced_through != null;
```

The empty guard is deliberately **skipped on the first tick** so a genuine cold
start can advance instead of wedging. So on an install where Gmail was never
authorized, the first tick reads "this window drained and had no mail", advances
the watermark, and that window of mail is never fetched again. Observed live: one
tick moved the watermark to 2026-08-25 with zero messages in the mailbox.

Throwing writes no state at all — verified, the watermark stayed `null` — and
puts an actionable `error` on Administration → Scheduled Jobs. This app has one
data source, so "Gmail is not connected" is not noise; it is the app's status.

### 3. The preview line is built from the unquoted body, not Gmail's snippet

Gmail's `snippet` includes quoted history. A "Thanks, done!" reply on a thread
full of requests previewed as `> Could you review the draft?` directly beside the
words **"No action items"** — which reads as the detector missing something
obvious, when ignoring a quote is exactly what it should do. The preview now comes
from the same `stripQuoted` text the detector scanned, falling back to Gmail's
snippet only for quote-only or body-less mail.

### 4. Route emptiness is the TABLE's, not the request's

`GET /messages` threw the "Gmail is not configured" 503 whenever the *filtered*
result was empty. Found by exercising the `needs-action` filter against a table
holding only action-free mail: the app was working perfectly and told the user
their mailbox was disconnected. The guard now confirms the table itself is empty
(one extra `head: true` count, only on the empty-and-unconfigured path) before
concluding this is a cold install.

`scripts/smoke-test-app.ts` reports `SKIPPED_NO_GET` for every route, because its
method parser is `/export\s+(?:async\s+)?function\s+(GET|…)/` — the form invariant
14 says **fails the build**. No route in this repo matches it, so the script's
"All routes look healthy" is vacuous for every app. Routes were verified by hand
instead. **Also worth raising with the platform owners.**

### Blocked: the Gmail OAuth grant

`connector_configs` has a `gmail` row (client id + secret saved), but the
connector reports `configured: false` — the authorize step was never completed, so
there is no refresh token. Nothing can pull real mail until an admin finishes it
at **Administration → Connectors → Gmail → Connect**, signing in *as the shared
mailbox account*, not as themselves.

After that, to finish verification:

```bash
npx tsx scripts/run-scheduled-jobs.ts    # twice
```

Both runs must be `ok` and well under 240s, and the second must do materially
less work — a smaller window or fewer pages in the `[sync]` log line.
