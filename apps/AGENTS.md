# How to Create or Modify an App

You are about to create or modify an app under `apps/`. **Read the sections below in order before writing any code.** The linked guides under `docs/apps/` are the authoritative reference; do not guess based on training data.

The same content is rendered in the UI at `/admin/apps` by [`src/components/apps/guide-tabs.tsx`](../src/components/apps/guide-tabs.tsx). Keep the tab component and the `docs/apps/*.md` files in sync until the UI is migrated to render markdown directly.

**Before you start: write a plan.** For anything beyond a trivial tweak, write a build plan to `docs/plans/YYYYMMDD_HHMM-<plan-name>.md` first (Context, decisions, file-level changes, verification). See [`../docs/plans/README.md`](../docs/plans/README.md).

## Hard invariants (the things agents most often get wrong)

Read these once, then read the guides. Most agent failures come from ignoring these rules, not from misreading the guides.

1. **Folder name *is* the slug.** It must match the slug used everywhere else. Use lowercase letters, digits, and underscores or hyphens. Do not put a separate `slug` field in `app.json` — the platform derives it from the folder name.
2. **Underscore-prefixed folders are templates** (`apps/_template/`). The registry skips them. Never ship a real app with a leading underscore.
3. **Widgets and client pages must never import connectors, `context`, or server modules.** They call their app's own API routes via `createAppClient(appSlug)`. Violating this leaks credentials to the browser.
4. **Do not hand-edit `src/generated/app-registry.ts`.** It is produced by `scripts/generate-project-registry.ts`. Run the generator after changes (see Verify below).
5. **Do not set `slug`, `hasPages`, or `hookCounts` in `app.json`** — the registry fills these in from the filesystem. **`lastUpdated` is the one exception:** it lives in the manifest, but it is written by `.githooks/pre-commit` (via `scripts/stamp-updated.ts`) on any commit that touches this app, never by hand. It records when the app last changed, and it is re-staged into that same commit automatically.
6. **`icon` must be a [Lucide](https://lucide.dev/icons/) name** in lowercase hyphenated form (e.g. `bar-chart`, not `BarChart`). Defaults to `box`.
7. **Widget `id` is derived from the component filename**, not declared. `widgets/sales-chart.tsx` → id `sales-chart`. Renaming a widget file breaks saved dashboards.
8. **Scoped-DB table names are auto-prefixed** with `_app_<slug>_`. Write bare names (`orders`) in migrations and queries; the platform adds the prefix.
9. **Never return raw `error.message` to the client.** Use `safeErrorMessage(err, "fallback")` from `@/lib/safe-error` in all catch blocks and Supabase error checks. Raw messages can leak table names, column names, or API details in production.
10. **Widgets and pages must use skeleton loading states.** Import `Skeleton` from `@/components/ui/skeleton` and render placeholder shapes that mirror the final layout while data is loading. Never show bare "Loading..." text or a lone spinner. For a refetch the *user* triggered (a filter or scope change), use `PendingState` from `@/components/ui/app-states` and name what's loading, rather than flashing an anonymous skeleton at someone who just clicked something.
11. **This is not vanilla Next.js.** See the root [`AGENTS.md`](../AGENTS.md). Read relevant docs in `node_modules/next/dist/docs/` before using an unfamiliar Next API.
12. **Every connector is tenant-scoped.** Apps declare connectors as bare strings in `connectors`; each has one admin-configured credential set shared by every user. When `context.connectors.<name>.configured` is `false`, the admin has not entered credentials — return 503 and render an error state. **Never** read `public.connector_configs` directly from app code; always go through `context.connectors.<name>`. See [`docs/apps/connectors.md`](../docs/apps/connectors.md).
13. **Connector-backed apps must pass the smoke test before shipping.** If `app.json` declares any `connectors`, run [`scripts/smoke-test-app.ts`](../scripts/smoke-test-app.ts) against the dev server. Verify the **guard path** (503 when the connector is unconfigured) *and* the **live data path** (real data of the shape the widget consumes) once it's configured. If no connector is configured yet, pause and ask the user to add credentials at `/admin/connectors` rather than declaring done.
14. **Every API route is a `defineRoute` declaration, and a bare handler fails the build.** `export const GET = defineRoute({ auth, roles, input, output, budget, handler })` — never `export async function GET`. The generator imports every `api/**/route.ts` and rejects anything else, because everything above `handler` has to be readable by the build (which cross-checks your roles), the gateway (which enforces auth and roles *before* your code runs), the proxy (which derives what is reachable without a session), and the generated client. Three consequences worth internalising:
    - **The handler returns plain data**, not a `NextResponse`. Throw `AppError.notFound()` / `.forbidden()` / `.unavailable()` and the pipeline picks the status. You no longer call `safeErrorMessage()` — it is applied for you (which is why invariant 9 is now the platform's job, not yours).
    - **An omitted `input` schema means the input is *unavailable*, not unvalidated.** Your handler receives `{}`. Query strings are coerced from your declared types, so `z.number()` gets a number without `z.coerce`.
    - **`auth` is a set, resolved strongest-first, and the platform enforces it.** `["session"]` is the default. Declaring `public`, `password`, or `key` widens `context.user` to nullable, so the *compiler* makes you handle the signed-out branch — that is the load-bearing safety property, not a convention — and `context.auth` names the tier that won. Strongest-wins is literal: a granted user gets `session` on a `["session","public"]` route, an ungranted one gets `public` rather than a 403. A route accepting `public`/`password` is derived into `/api/p/<slug>/...`; don't also declare it in `apiVisibility`, and if you do, the build requires the two to agree. **`roles` is enforced by the platform before your handler runs** — default-deny, and a platform admin does NOT bypass an app role. `budget.connectorCalls` (default 100) caps fan-out; raising it to make a failing route pass is usually ignoring a real N+1.
15. **App roles are isolated and enforced by the app, not the platform.** Declare per-app roles as `{ key, label }` objects in `app.json` (`roles`) with an optional `defaultRole` key. The platform stores each user's role on their grant and exposes `context.user.hasRole([...keys])` (true if the user holds any of the given keys), but it does **not** enforce any policy — your route handlers must call `hasRole` and decide. `hasRole` is pure: it ignores `isAdmin`, so write `context.user.isAdmin || context.user.hasRole([...])` if admins should bypass. A user with no assigned role (including everyone on a `global` app) resolves to `defaultRole`. Public/password handlers have `context.user === null` and no roles. See [`docs/apps/roles.md`](../docs/apps/roles.md).
16. **Web Push goes through the platform, not the browser APIs.** Set `"notifications": true` and send only from an API route via `context.notifications.send({ userIds, ... })`. Opt users in from a user gesture with `enablePushNotifications()` from `@/lib/apps/sdk`. Never call `Notification`, `navigator.serviceWorker`, or `PushManager` directly from a widget/page, and never write to `public.push_subscriptions`. See [`docs/apps/notifications.md`](../docs/apps/notifications.md).
17. **Scheduled jobs are declared, not hand-wired.** Add a `schedules: [{ name, everyMinutes }]` (or `{ name, cron, timezone? }`) entry to `app.json` and put the handler at `jobs/<name>.ts` (default export `async (ctx: SystemAppContext) => void`). Each job sets **exactly one** cadence: `everyMinutes` (≥ 5 and a multiple of 5, interval-based) or a 5-field `cron` expression (wall-clock, optional IANA `timezone`, default UTC). Both are evaluated at 5-minute resolution. The handler runs with a user-less system context (tenant connectors + scoped db + notifications) — never assume a user. Do not start your own timers/intervals, and never read or write `public.app_scheduled_jobs` / `public.app_job_runs` from app code — the platform scheduler owns them. See [`docs/apps/scheduled-jobs.md`](../docs/apps/scheduled-jobs.md).
18. **Cross-app data goes through App Services, never around them.** An app must never read another app's `_app_<other>_*` tables, import the raw DB client (`@/lib/db`), or call another app's routes. To request data from another app, the provider declares `provides: [{ name, audience, consumers }]` (handler at `services/<name>.ts`) and the consumer declares `consumes: [{ app, service }]`; the platform brokers the call via `context.services.request(provider, service, params)`. Two-sided consent is default-deny and build-enforced. The broker runs the provider's handler with the *provider's* scoped context and re-authorizes the user in the provider's own terms — a provider must never trust that the consumer checked. `audience: "user"` (default) forbids privilege escalation; `audience: "app"` is an explicit service-account opt-in. `context.services` is server-only (routes/jobs) and `null` on the public surface. See [`docs/apps/app-services.md`](../docs/apps/app-services.md).
19. **MCP tools are declared, read-only, and consented to.** To let Claude answer questions using your app's data, declare `mcp: [{ name, description, sources, hint?, notCovered? }]` in `app.json` and put the handler at `mcp/<name>.ts`, exporting **both** `inputSchema` (a Zod object — it becomes the tool's JSON Schema) and a default `async (ctx: McpToolContext, input) => result`. Max 5 tools per app (the build fails at 6); aim for 2–3, because the client sees one flat list pooled across every consented app **and every other MCP server the user has connected**. That shared list is why **descriptions describe data, never claim a topic**: a tool saying "start here for any question about X" reads as an instruction rather than a capability and outranks the user's other connectors on questions they'd answer better, so the build *rejects* that phrasing outright. Bound your claim instead — `sources` (connector slugs your app declares, or `"ros"`; list only what the handler actually reads) and `notCovered` (concrete exclusions, pointing at the tool that does cover it). Tools are **read-only**: `ctx.db` has no `insert`/`update`/`upsert`/`delete` (absent from the type *and* trapped at runtime), there is no `ctx.notifications`, and every connector call you make must be a read — the platform can't check that one, so a reviewer must. A tool runs as the connecting user with your app's roles resolved, and is reachable only when the user consented to your app *and* still holds a grant for it; re-authorize in your own terms anyway. Reuse the same builders your routes use so a model and the UI can never quote different numbers, and shape results for a model (facts, not colors and embed URLs; hard 1 MB cap). Never bypass the broker or hand-roll an MCP endpoint. See [`docs/apps/mcp.md`](../docs/apps/mcp.md).
20. **Telemetry events are declared, not free-form.** To track key usage, declare each event in `app.json` `telemetry` (`[{ name, description? }]`) and record it via `context.telemetry?.track(name, properties?)` from an API route or job, or the client SDK `track(appSlug, name, properties?)` from a widget/page. Undeclared event names are dropped. Never write `public.telemetry_events` directly, and keep `properties` free of PII/secrets. An app that declares no events gets no `context.telemetry` client. See [`docs/apps/telemetry.md`](../docs/apps/telemetry.md).
21. **Background data work is incremental, budgeted, and cached.** A job that pulls from a connector or warehouse must do three things. **Budget by wall clock:** set a deadline under the ~4-minute timeout, check `ctx.signal.aborted || Date.now() >= deadline` at every item/stage/page boundary, and stop by breaking with progress committed — never by item count alone, because per-item cost varies and a count can't predict runtime. **Sync incrementally:** advance a persisted watermark instead of re-reading everything, and **never persist a provider pagination cursor across ticks** — cursors expire in less time than the interval between runs, which cost one app a 19-day outage. **Serve reads from your own tables:** materialize into a snapshot or cache table so a page never waits on the connector, and never overwrite a good snapshot with an empty upstream result. See [`docs/apps/data-freshness.md`](../docs/apps/data-freshness.md).

22. **No raw palette colours in app UI — and colours fork in `globals.css`, never in an app.** Text, surfaces, and status come from the semantic tokens (`text-foreground`, `bg-card`, `bg-primary`, `text-success` / `text-warning` / `text-destructive`). Colour that *distinguishes* rather than *grades* — chart series, category chips, column accents — uses the categorical ramp `cat-1`…`cat-6`; never borrow `destructive`/`warning`/`success` for decoration, or a category chip will tell the user that category is an error. Never write `text-<palette>-<n>`, a raw hex, or an opaque `bg-white` / `bg-gray-*` surface — and never write a `dark:` variant. Alpha over a known ground (`bg-white/10` on a navy panel, `bg-black/70` as a scrim) is fine; the rule targets opaque fills pretending to be a theme surface. The platform is light-only today, but `.dark` is kept complete and AA-correct so shipping dark mode stays a one-file change instead of an audit of every app — per-app `dark:` variants are exactly what would destroy that. Lint-enforced for `apps/**` by `eslint.config.mjs`. **And a legal token is not a legal element:** `globals.css` verifies each token against the page background and against its own foreground, never against another token, so `bg-muted` + `text-muted-foreground` on one element is 4.34:1 and fails — one of ~215 such elements across 16 apps that CI used to pass. `mos-design/no-low-contrast-token-pairs` computes the ratio per element and per hover/focus state; it warns today rather than errors, because it flags that pre-existing backlog, so treat a warning on code you touched as an error. See [`docs/apps/ux.md`](../docs/apps/ux.md#color--contrast) and [Verified pairs](../docs/apps/ux.md#verified-pairs-two-legal-tokens-can-make-an-illegal-element).
23. **Every empty state names its cause.** "The user emptied a filter", "the filter matched nothing", and "there's no data yet" are three different problems with three different fixes; one generic blank box tells the user which one they're in: none. Use `EmptyState` from `@/components/ui/app-states` and pass `cause`. A `no-filter` state additionally **requires** an `action` — the type signature enforces it, because a filter the user emptied is always recoverable by the user.
24. **Read-only users see controls omitted, not disabled.** Gate on a fail-closed capability context (default `false` until `/me` confirms) and pass `undefined` for the affordance — e.g. `SectionCard`'s `footer` — rather than rendering a greyed-out button. A disabled control advertises a capability the user doesn't have and sends them hunting for why. This is UX only: the route must enforce the role independently via `context.user.hasRole`. See [`docs/apps/app-shell.md`](../docs/apps/app-shell.md#permission-aware-ui).

25. **Breaking a platform rule is possible, declared, and visible — never silent.** An app that genuinely must escape a guarantee names it in `app.json` under `escapes: [{ rule, reason }]`, from a closed set (`raw-html`, `raw-response`, `output-validate-dev-only`, `process-env`, `raw-fetch`). An unknown rule name fails the build, because a typo'd escape reads as "declared" to a reviewer while enforcing nothing, and `reason` must be a sentence someone can act on. Related: an app reads configuration through `context.env` (declared under `env`, admin-set, `password` values encrypted at rest) rather than `process.env`, which can reach the platform's own secrets; and it reaches the network through a connector or `context.http`, bounded by the manifest's `egress` hostname allowlist. There is **no** `disableOsStyles` — the design system has no opt-out.

Authoritative types: [`src/lib/apps/types.ts`](../src/lib/apps/types.ts). Canonical template: [`apps/_template/`](_template/).

## Verify (run these before reporting done)

From the repo root:

1. `npx tsx scripts/generate-project-registry.ts` — regenerates `src/generated/app-registry.ts`. Confirm your app appears with the expected widgets **and routes**. The generator imports every `api/**/route.ts`: a bare handler export, a JSON route with no `output`, a route file exporting no HTTP method, a role your app never declared, or an `apiVisibility` entry that contradicts a route's own `auth` each abort the build. The generator **schema-validates `app.json`** (via `scripts/manifest-schemas.ts`): an unknown field, a wrong-typed value, a bad `defaultRole`, or an auto-generated field set by hand **aborts the whole build** with a message pointing at the offending path. Keep the manifest within the fields in `src/lib/apps/types.ts`.
2. `npm run typecheck` — catches manifest/type drift.
3. If you changed `"database": true` or added migrations: `npm run migrate`.
4. For UI changes, load `/apps/<slug>` in the dev server and exercise the golden path plus one edge case. Don't claim "done" on a UI change you haven't opened in a browser.
5. If `app.json` declares `connectors`, run `npx tsx scripts/smoke-test-app.ts <slug>` against the dev server (see the script header for `SMOKE_COOKIE` setup). Every connector-backed route must classify as `OK_DATA`, `OK_NOT_CONNECTED`, `UNCONFIGURED_TENANT`, or a deliberately-skipped `SKIPPED_*`. Anything else (especially `GUARD_MISMATCH`) is a bug. See the failure-triage section in [`.claude/commands/mix-app.md`](../.claude/commands/mix-app.md).
6. If `app.json` declares `mcp` tools, run `npx @modelcontextprotocol/inspector` against `http://localhost:3000/api/mcp`, complete the OAuth flow, and **call each tool with real arguments**. Read the result as if you were the model: is it answerable, and is anything in there noise? See [`docs/apps/mcp.md`](../docs/apps/mcp.md#verify).
7. If `app.json` declares `schedules`, or the app caches connector/warehouse data, run `npx tsx scripts/run-scheduled-jobs.ts` **twice**. At `/admin/scheduled-jobs`, confirm both runs are `ok` with a duration well under 240s, and that the **second run did materially less work than the first** — the log line should show a smaller window, fewer pages, or fewer items. A second run that costs the same as the first is a full refresh wearing a scheduler's clothes; fix it per [`docs/apps/data-freshness.md`](../docs/apps/data-freshness.md). Then load the page and confirm the read path still renders from the snapshot with the upstream connector unconfigured.

## Anti-patterns (do not do these)

- Importing a connector or `context` in a widget or client page.
- Calling another app's API routes from your app.
- Editing `src/generated/*-registry.ts` by hand.
- Adding fields to `app.json` that aren't in `src/lib/apps/types.ts`.
- Using an `icon` value that isn't a Lucide icon name.
- Shipping a real app under a folder starting with `_`.
- Using non-lowercase or whitespace-bearing folder names.
- Writing prefixed table names (`_app_…`) in migrations — the platform adds the prefix.
- Returning `error.message` or `err.message` directly in API responses — use `safeErrorMessage()` instead.
- Showing "Loading..." text or a bare spinner while fetching data — use `Skeleton` components that mirror the final layout.
- Fetching user-provided URLs server-side without validating the hostname — block private IP ranges and cloud metadata endpoints to prevent SSRF.
- Calling `Notification`, `navigator.serviceWorker`, or `PushManager` directly, or writing to `public.push_subscriptions` — use `enablePushNotifications()` (client) and `context.notifications.send()` (API route) instead.
- Writing anything from an `mcp/` handler, or calling a connector method that mutates. MCP tools are read-only; `ctx.db` blocks writes, but a mutating connector call is on you to avoid.
- Declaring more MCP tools than an app needs, or shipping a tool whose `description` doesn't say what it returns and when to use it — that text is all the model gets.
- Duplicating query logic in an `mcp/` handler instead of sharing the builder its API route already uses. The tool and the UI must never quote different numbers.
- Persisting a provider pagination cursor in your state table between job runs — it will have expired by the next tick. Use a date window instead.
- Bounding a job by item count instead of a wall-clock deadline, or checking the budget only at the top of the run instead of at every boundary.
- Overwriting a good snapshot with an empty upstream result, or reporting a missing snapshot as zeros rather than as unknown.
- An unbounded `delete()` before re-inserting a window's worth of rows — scope it to the window you actually refetched, or a shallow sync will erase a deep backfill.
- Calling a connector on the request path for data a scheduled job could have materialized, or triggering a cache rebuild from an `mcp/` handler instead of serving what's cached and reporting its age.
