# How to Create or Modify an App

You are about to create or modify an app under `apps/`. **Read the sections below in order before writing any code.** The linked guides under `docs/apps/` are the authoritative reference; do not guess based on training data.

The same guides are published on mixos.org, which the admin pages link to.

**Before you start: write a plan.** For anything beyond a trivial tweak, write a build plan to `apps/<slug>/plans/YYYYMMDD_HHMM-<plan-name>.md` first — **beside the app it describes**, so the design history travels with the code (Context, decisions, file-level changes, verification). Every app has a `plans/` directory, [`_template`](_template/plans/) included, so a scaffolded app inherits the convention. A change to the platform itself (`src/`, `scripts/`, the build) is a *platform* plan and goes to `docs/plans/` instead. See [`../docs/plans/README.md`](../docs/plans/README.md).

## Hard invariants (the things agents most often get wrong)

Read these once, then read the guides. Most agent failures come from ignoring these rules, not from misreading the guides.

1. **Folder name *is* the slug.** It must match the slug used everywhere else. Use lowercase letters and digits, in words joined by single hyphens or underscores (`sales-tracker`); the build refuses anything else, because the slug also names the app's database schema. It refuses `release-notes` too, which is App Manager's page at `/apps/release-notes`. Do not put a separate `slug` field in `app.json` — the platform derives it from the folder name. **A slug published to mixos.org ends in an id**, eight hex characters minted when it is first listed (`sales-tracker-3f9a2c1b`), so two people's `tasks` can be installed side by side; rename your own folder to the listed slug with `npm run rename -- app/<slug> --to <listed-slug>`. **Rename an app only with `npm run rename`**: it moves the folder, rewrites the app's own slug in its code and other apps' references to it, and records the rename in `extension-renames.json`, from which the release step moves every instance's grants, settings, widgets, keys and tables to the new slug. Renaming the folder by hand makes a new app: it arrives inactive with none of the old slug's grants, settings or tables, which the release step keeps under the old slug. An app whose folder comes back with different files arrives switched off until an admin activates it again. So does an app that is a different extension than the one an instance knew under its slug, by its `.registry.json` (a local app reinstalled from the Registry, or a release from another repository): its API keys are revoked too, and activating it needs its slug typed. To remove an app from a checkout, use **Remove** on Admin > Apps or `npm run remove -- app/<slug>` rather than deleting the folder by hand: it refuses while another app uses the app's services or hooks, and hands back the commit. Each instance keeps the app's data until an admin deletes it there with **Delete data…**, which drops its schema and role; a later app with the same slug then inherits nothing.
2. **Underscore-prefixed folders are templates** (`apps/_template/`). The registry skips them. Never ship a real app with a leading underscore. It skips dot-prefixed folders too, such as a copy set aside as `apps/.old-<slug>/`, so never start an app's folder name with a dot either.
3. **Widgets and pages must never import connectors, the DB, `context`, or their app's own `lib/server`.** The build refuses all of them (invariant 31). A widget calls its route with `createAppClient<"my-app">(appSlug).call("GET /items", input)` — typed against the route's own schemas. A **server page** calls `await callAppRoute("my-app", "GET /items", input)`, which runs the identical gateway pipeline in-process. Reaching around either leaks credentials to the browser or skips every check the gateway performs.
4. **Do not hand-edit `src/generated/app-registry.ts`.** It is produced by `scripts/generate-project-registry.ts`. Run the generator after changes (see Verify below).
5. **Do not set `slug`, `hasPages`, or `hookCounts` in `app.json`** — the registry fills these in from the filesystem. **`lastUpdated` is the one exception:** it lives in the manifest, but it is written by `.githooks/pre-commit` (via `scripts/stamp-updated.ts`) on any commit that touches this app, never by hand. A merge that only brings in another branch's change to the app keeps that branch's date. It records when the app last changed, and it is re-staged into that same commit automatically. An app installed from the Registry is never stamped: its `.registry.json` records the files that were verified, and its date is its publisher's.
6. **`icon` must be a [Lucide](https://lucide.dev/icons/) name** in lowercase hyphenated form (e.g. `bar-chart`, not `BarChart`). Defaults to `box`.
7. **Widget `id` is derived from the component filename**, not declared. `widgets/sales-chart.tsx` → id `sales-chart`. Renaming a widget file breaks saved dashboards.
8. **An app's tables live in its own schema, and its migrations may only build them.** With `"database": true` the app gets the schema `app_<slug>`, owned by a role of its own; without it, shipping `migrations/` fails the build. Write bare names (`orders`) in migrations and in `context.db.table(...)` — nothing rewrites them. Every statement is checked before it runs, by the build and by the release step: tables, indexes, views, sequences, enum types and their rows in your schema are allowed; triggers, functions, `DO`, policies, grants, `SET`, extensions, anything outside your schema, and function calls beyond a short list of pure built-ins (`now()`, `gen_random_uuid()`, `lower()`, ...) are refused. For an `updated_at` that maintains itself, list the column under `updatedAt` in `app.json` and the platform adds the trigger. See [`docs/apps/database.md`](../docs/apps/database.md#what-a-migration-may-contain).
9. **Never return raw `error.message` to the client.** Throw instead: the pipeline turns any error into a response through `safeErrorMessage()`, and an `AppError` picks the status (invariant 14). A `raw: true` route that builds its own error Response must not put an error's message in it. Raw messages can leak table names, column names, or API details in production.
10. **Compose from the primitives; the raw elements are lint errors.** A `<button>`, `<input>`, `<select>`, `<textarea>` or `<table>` in `apps/**` fails lint, which CI runs, as does a literal copy of the card shell. Use `Button`/`IconButton` (where `busy` makes the pending state one prop), `Input`/`Select`/`Checkbox` inside `Field` (which owns the id, so a label can never point at nothing), `DataTable` (which ships the matching `TableSkeleton`), and `Card`/`SectionCard` (cards are **flat — no `shadow-*`** — and inset by a single `p-5`; a bordered group *inside* a card is `rounded-md border border-border p-4` with no `bg-card`, because giving it a fill makes a card inside a card). **For anything async, use `useAppQuery` + `AsyncView`**: it will not let you render data without also supplying a layout-matching `skeleton` and an `empty` that names its `cause`, and it handles refetching (keeping the old data visible) and errors for you. See [`docs/apps/ux.md`](../docs/apps/ux.md#compose-from-the-primitives).
11. **This is not vanilla Next.js.** See the root [`AGENTS.md`](../AGENTS.md). Read relevant docs in `node_modules/next/dist/docs/` before using an unfamiliar Next API.
12. **Connectors are declared with a version, and an app changes data only when it says so.** Each entry in `connectors` and `optionalConnectors` is `{ "name", "version", "access"? }`: `version` is the connector version the app was built against (read it from the connector's `connector.json`; any later release with the same major version satisfies it, and the build fails on one that doesn't), and `"access": "write"` is required to call a method the connector declares `mutates`. The platform hands the app its connector narrowed to the declared methods, so a write the entry didn't ask for, or a reach around the declaration (`request()`), throws. A write also needs the connector's admin to allow changes; until then it fails with a `forbidden` error that names what to do, and an app that requires the connector can't be activated. **If a connector lacks what the app needs, don't shape the connector for the app**: if the provider has the operation, add it to the connector as a plain mirror of it, a new minor version, in a change of its own, and name that version here; otherwise build it in the app's `lib/server/` from the methods there are ([connectors/AGENTS.md](../connectors/AGENTS.md#the-contract-a-connector-mirrors-its-provider)). **Connectors are tenant-scoped unless the connector says otherwise.** Most have one admin-configured credential set shared by every user: when `context.connectors.<name>.configured` is `false`, the admin has not entered credentials — answer 503 (`throw AppError.unavailable()`) and render an error state. A connector whose `connector.json` sets `"userScoped": true` signs each person into their own account instead. It is absent from `context.connectors` until that user connects, which a route answers with `{ connected: false }` and a Connect prompt, not a 503 ([user-scoped connectors](../docs/apps/connectors.md#user-scoped-per-user-connectors)). A job has no user, so the build fails an app that declares a user-scoped connector alongside `schedules` or `sync`. **Never** read `public.connector_configs` directly from app code; always go through `context.connectors.<name>`. See [`docs/apps/connectors.md`](../docs/apps/connectors.md).
13. **Every app must pass the smoke test before shipping.** Activate the app, grant it to the user you test as, and run [`scripts/smoke-test-app.ts`](../scripts/smoke-test-app.ts) against the running server. It calls every route that user can reach with GET and HEAD, never POST, PUT, PATCH or DELETE, and fails on a 5xx, a network error or a timeout. A route whose connector isn't configured fails with a 503: pause and ask the user to add credentials at `/admin/connectors` rather than declaring done. Once it's configured, check the **live data path** returns data of the shape the widget consumes. A pull request that changes an app runs this test in CI too, on a fresh instance with no credentials, where a route that answers 503 UNAVAILABLE is skipped rather than failed.
14. **Every API route is a `defineRoute` declaration, and a bare handler fails the build.** `export const GET = defineRoute({ auth, roles, input, output, budget, handler })` — never `export async function GET`. The generator imports every `api/**/route.ts` and rejects anything else, because everything above `handler` has to be readable by the build (which cross-checks your roles), the gateway (which enforces auth and roles *before* your code runs, and decides from them which routes a caller without a session can reach), and the generated client. Three consequences worth internalising:
    - **The handler returns plain data**, not a `NextResponse`. Throw `AppError.notFound()` / `.forbidden()` / `.unavailable()` and the pipeline picks the status. You don't call `safeErrorMessage()` — it is applied for you (which is why invariant 9 is the platform's job, not yours).
    - **An omitted `input` schema means the input is *unavailable*, not unvalidated.** Your handler receives `{}`. Query strings are coerced from your declared types, so `z.number()` gets a number without `z.coerce`.
    - **`auth` is a set, resolved strongest-first, and the platform enforces it.** `["session"]` is the default. Declaring `public`, `password`, or `key` widens `context.user` to nullable, so the *compiler* makes you handle the signed-out branch — that is the load-bearing safety property, not a convention — and `context.auth` names the tier that won. Strongest-wins is literal: a granted user gets `session` on a `["session","public"]` route, an ungranted one gets `public` rather than a 403. A route accepting `public`/`password` is derived into `/api/p/<slug>/...`; its `auth` is the only place that says so. **`roles` is enforced by the platform before your handler runs** — default-deny, and a platform admin does NOT bypass an app role. `budget.connectorCalls` (default 100) caps fan-out; raising it to make a failing route pass is usually ignoring a real N+1.
15. **App roles are isolated to the app, and a route's `roles` are enforced by the platform.** Declare per-app roles as `{ key, label }` objects in `app.json` (`roles`) with an optional `defaultRole` key. The platform stores each user's role on their grant. A route that declares `roles` is checked before its handler runs: default-deny, and a platform admin does not bypass it (invariant 14). Inside a handler, `context.user.hasRole([...keys])` (true if the user holds any of the given keys) is for finer branching, such as which fields to include. `hasRole` is pure: it ignores `isAdmin`, so write `context.user.isAdmin || context.user.hasRole([...])` if admins should bypass. A user with no assigned role (including everyone on a `global` app) resolves to `defaultRole`. When a `public`, `password` or `key` caller wins, `context.user` is `null` and there are no roles. See [`docs/apps/roles.md`](../docs/apps/roles.md).
16. **Web Push goes through the platform, not the browser APIs.** Set `"notifications": true` and send from an API route or a scheduled job via `context.notifications.send({ userIds, ... })`. Opt users in from a user gesture with `enablePushNotifications()` from `@/lib/apps/sdk`. Never call `Notification`, `navigator.serviceWorker`, or `PushManager` directly from a widget/page, and never write to `public.push_subscriptions`. See [`docs/apps/notifications.md`](../docs/apps/notifications.md).
17. **Scheduled jobs are declared, not hand-wired.** Add a `schedules: [{ name, everyMinutes }]` (or `{ name, cron, timezone? }`) entry to `app.json` and put the handler at `jobs/<name>.ts` (default export `async (ctx: SystemAppContext) => void`). Each job sets **exactly one** cadence: `everyMinutes` (≥ 5 and a multiple of 5, interval-based) or a 5-field `cron` expression (wall-clock, optional IANA `timezone`, default UTC). Both are evaluated at 5-minute resolution. The handler runs with a user-less system context (tenant connectors + scoped db + notifications) — never assume a user. Do not start your own timers/intervals, and never read or write `public.app_scheduled_jobs` / `public.app_job_runs` from app code — the platform scheduler owns them. See [`docs/apps/scheduled-jobs.md`](../docs/apps/scheduled-jobs.md).
18. **Cross-app data goes through App Services, never around them.** An app must never read another app's tables, import the raw DB client (`@/lib/db`) or another app's code, or call another app's routes. The build refuses the imports, and a `callAppRoute` with any slug but the app's own (invariant 31). To request data from another app, the provider declares `provides: [{ name, audience, consumers }]` (handler at `services/<name>.ts`) and the consumer declares `consumes: [{ app, service }]`; the platform brokers the call via `context.services.request(provider, service, params)`. Two-sided consent is default-deny and build-enforced. The broker runs the provider's handler with the *provider's* scoped context and re-authorizes the user in the provider's own terms — a provider must never trust that the consumer checked. `audience: "user"` (default) forbids privilege escalation; `audience: "app"` is an explicit service-account opt-in. `context.services` is server-only (routes/jobs); with no user (a job, or a `public`, `password` or `key` caller) it reaches only `audience: "app"` services. See [`docs/apps/app-services.md`](../docs/apps/app-services.md).
19. **MCP tools are declared, read-only, and consented to.** To let Claude answer questions using your app's data, declare `mcp: [{ name, description, sources, hint?, notCovered? }]` in `app.json` and put the handler at `mcp/<name>.ts`, exporting **both** `inputSchema` (a Zod object — it becomes the tool's JSON Schema) and a default `async (ctx: McpToolContext, input) => result`. Max 5 tools per app (the build fails at 6); aim for 2–3, because the client sees one flat list pooled across every consented app **and every other MCP server the user has connected**. That shared list is why **descriptions describe data, never claim a topic**: a tool saying "start here for any question about X" reads as an instruction rather than a capability and outranks the user's other connectors on questions they'd answer better, so the build *rejects* that phrasing outright. Bound your claim instead — `sources` (connector slugs your app declares, or `"mixos"`; list only what the handler actually reads) and `notCovered` (concrete exclusions, pointing at the tool that does cover it). Tools are **read-only**: `ctx.db` has no `insert`/`update`/`upsert`/`delete` (absent from the type *and* trapped at runtime), there is no `ctx.notifications`, a connector exposes only the methods it declares as reads (one declared `mutates`, or not declared at all — `request()` included — throws), and a provider you reach through `ctx.services` runs read-only too. The platform trusts a connector's declarations, so a method that writes without being declared `mutates` is still on you to avoid. A tool runs as the connecting user with your app's roles resolved. It starts off and is reachable only once an admin turns it on, on your app's MCP tab, and then only while the user has consented to your app *and* still holds a grant for it; re-authorize in your own terms anyway. Reuse the same builders your routes use so a model and the UI can never quote different numbers, and shape results for a model (facts, not colors and embed URLs; hard 1 MB cap). Never bypass the broker or hand-roll an MCP endpoint. See [`docs/apps/mcp.md`](../docs/apps/mcp.md).
20. **Telemetry events are declared, not free-form.** To track key usage, declare each event in `app.json` `telemetry` (`[{ name, description? }]`) and record it via `context.telemetry?.track(name, properties?)` from an API route or job, or the client SDK `track(appSlug, name, properties?)` from a widget/page. Undeclared event names are dropped. Never write `public.telemetry_events` directly, and keep `properties` free of PII/secrets. An app that declares no events gets no `context.telemetry` client. See [`docs/apps/telemetry.md`](../docs/apps/telemetry.md).
21. **Background data work is incremental, budgeted, and cached.** A job that pulls from a connector or warehouse must do three things. **Budget by wall clock:** set a deadline under the ~4-minute timeout, check `ctx.signal.aborted || Date.now() >= deadline` at every item/stage/page boundary, and stop by breaking with progress committed — never by item count alone, because per-item cost varies and a count can't predict runtime. **Sync incrementally:** advance a persisted watermark instead of re-reading everything, and **never persist a provider pagination cursor across ticks** — cursors expire in less time than the interval between runs, which cost one app a 19-day outage. **Serve reads from your own tables:** materialize into a snapshot or cache table so a page never waits on the connector, and never overwrite a good snapshot with an empty upstream result. See [`docs/apps/data-freshness.md`](../docs/apps/data-freshness.md).

22. **No raw palette colours in app UI — and colours fork in the active theme, never in an app.** Text, surfaces, and status come from the semantic tokens (`text-foreground`, `bg-card`, `bg-primary`, `text-success` / `text-warning` / `text-destructive`). Colour that *distinguishes* rather than *grades* — chart series, category chips, column accents — uses the categorical ramp `cat-1`…`cat-6`; never borrow `destructive`/`warning`/`success` for decoration, or a category chip will tell the user that category is an error. Never write `text-<palette>-<n>`, a raw hex, or an opaque `bg-white` / `bg-gray-*` surface — and never write a `dark:` variant. Alpha over a known ground (`bg-white/10` on a navy panel, `bg-black/70` as a scrim) is fine; the rule targets opaque fills pretending to be a theme surface. A theme declares one palette, and the dark look is a separate theme (MixOS Dark) an admin picks; the platform stamps only `data-theme` on `<html>`. So an app renders correctly under every theme without containing the word `dark` anywhere, and a per-app `dark:` variant, a second answer the contrast gate can't see, is a lint error rather than a convention. Lint-enforced for `apps/**` by `eslint.config.mjs`. **And a legal token is not a legal element:** the theme build verifies each token against the page background and against its own foreground, never against another token, so `bg-muted` + `text-muted-foreground` on one element is 4.34:1 and fails — one of ~215 such elements across 16 apps that CI used to pass. `mixos-design/no-low-contrast-token-pairs` computes the ratio per element, per hover/focus state and under every installed theme, and it is a lint error. See [`docs/apps/ux.md`](../docs/apps/ux.md#color--contrast), [Verified pairs](../docs/apps/ux.md#verified-pairs-two-legal-tokens-can-make-an-illegal-element), and [`docs/themes/tokens.md`](../docs/themes/tokens.md) for the token contract itself.
23. **Every empty state names its cause.** "The user emptied a filter", "the filter matched nothing", and "there's no data yet" are three different problems with three different fixes; one generic blank box tells the user which one they're in: none. Use `EmptyState` from `@/components/ui/app-states` and pass `cause`. A `no-filter` state additionally **requires** an `action` — the type signature enforces it, because a filter the user emptied is always recoverable by the user.
24. **Read-only users see controls omitted, not disabled.** Gate on a fail-closed capability context (default `false` until `/me` confirms) and pass `undefined` for the affordance — e.g. `SectionCard`'s `footer` — rather than rendering a greyed-out button. A disabled control advertises a capability the user doesn't have and sends them hunting for why. This is UX only: the route must enforce the role independently, through its `roles` or `context.user.hasRole`. See [`docs/apps/app-shell.md`](../docs/apps/app-shell.md#permission-aware-ui).

25. **An app reaches the environment and the network by declaration, and no other way.** Any reference to `process`, and any raw network access — `fetch`, `WebSocket`, `EventSource`, `XMLHttpRequest`, the `http`/`https`/`net` family, an HTTP client package — fails the build, not just lint: the registry generator reads every app's source on every build and every Registry install, and skips an app that reaches one. Neither is escapable. Read configuration through `context.env` (declared under `env` in `app.json`, admin-filled, `password` values encrypted at rest) — the raw environment carries `CONNECTOR_ENCRYPTION_KEY` and `DATABASE_URL`. Reach the network through a connector, or `context.http`, which checks the hostname against the manifest's `egress` allowlist, resolves it, re-checks every returned address against private ranges, and repeats both on each redirect hop. See [`docs/security-architecture.md` §24](../docs/security-architecture.md#24-environment-containment).

26. **Incremental sync is declared, not hand-rolled.** Add `sync: [{ name, schedule, source, window, budgetMs }]` to `app.json` and write two functions at `sync/<name>.ts` via `defineSync` — `fetchPage` and `upsert`. The platform owns the watermark, the wall-clock budget checked at every page boundary, window halving and relaxing, the empty-result guard, and the state table. **The provider's cursor never leaves the run**, which is what makes the 19-day expired-cursor outage unrepresentable rather than merely documented. See [`docs/apps/data-freshness.md`](../docs/apps/data-freshness.md).

27. **Cross-app hooks need two-sided consent.** An emitter declares `emits: [{ name, consumers }]`; a listener declares `listensTo: [{ app, hook }]`. A `listensTo` the emitter does not allow fails the build; code that listens to another app's hook without a `listensTo`, or fires one, gets the app skipped by the build, and the registrar refuses the same at runtime. This is the same default-deny App Services has always had, applied to the one cross-app channel that never had it. Firing your own hooks, and listening to core hooks, needs no declaration.

28. **One platform rule can be broken, and only on the record.** A route that must own its Response — a file download, a stream, a redirect — sets `raw: true`, and `app.json` must say so: `escapes: [{ "rule": "raw-response", "reason": "…" }]`. A raw route without that declaration keeps the whole app out of the registry, a declaration with no raw route draws a warning, and an admin sees each escape and its reason in the app's details. `raw-response` is the whole set: an unknown rule name fails the build, because a typo'd escape reads as "declared" to a reviewer while enforcing nothing, and `reason` must be a sentence someone can act on. **Not** escapable: the environment and the network (invariant 25); what app code imports (invariant 31); raw HTML — `dangerouslySetInnerHTML`, `innerHTML`, `insertAdjacentHTML` and `document.write` fail the build, and formatted text you did not write goes through `Markdown` from `@/components/ui/markdown`, which drops raw HTML; `eval` and `new Function`; and output validation, which runs on every response. There is **no** `disableOsStyles` — the design system has no opt-out.

29. **Listing screenshots are declared and live in `screenshots/`, never in the README.** Put images under `apps/<slug>/screenshots/` and declare them in `app.json` as `screenshots: [{ file, alt?, caption? }]`, with `file` carrying its `screenshots/` prefix. An image referenced from `README.md` is *not* an alternative and never was: the listing renderer resolves a relative path against mixos.org rather than your repo, so it publishes as a dead link the author never sees, because the same file renders fine on GitHub. The build verifies and measures each declared file and fills in `url`, `width` and `height` — never write those by hand. Limits: `.png`/`.jpg`/`.webp` only (**no SVG** — a screenshot is a raster, and an SVG is a script-bearing document served from an unauthenticated URL), max 8, max 2 MB each, min 640px wide. Only declared files are published, so a draft left in the directory stays local. See [`docs/apps/assets.md`](../docs/apps/assets.md#screenshots).

30. **Brand hooks are declared, registered in `hooks.ts`, and bounded.** To change the install's name or its marks, register `brand-name`, `menu-bar-logo` or `login-logo` in `apps/<slug>/hooks.ts`, the entrypoint the platform loads before rendering the brand, and declare them in `app.json` as `branding: { hooks, reason, logos? }`. The build fails if the declaration and `hooks.ts` disagree in either direction, or if a brand hook is registered anywhere else. A logo filter returns `null`, its input unchanged, or the `file` of one of the app's own declared logos under `branding/`. It never returns a URL, and anything else is discarded. Filters run in a fixed order (priority, then slug), and all of a slot's filters share one second per request. A slot the active theme claims in its own `branding` is the theme's, and your filter for it does not run. See [`docs/apps/hooks.md`](../docs/apps/hooks.md#brand-hooks).

31. **App code imports its own files, a published list of platform modules, and a few packages. Nothing else.** The list is in [`docs/apps/architecture.md`](../docs/apps/architecture.md#what-an-app-can-import), generated from [`src/lib/apps/import-policy.mjs`](../src/lib/apps/import-policy.mjs): the route contract and its errors, `callAppRoute`, the browser SDK, `useAppQuery`, `createSwrCache`, `defineSync`, the widget presets and the UI primitives, some of them by name only; and the packages `react`, `zod`, `lucide-react`, `next/link`, `next/navigation` and `next/font/*`. No Node built-ins, no other package, and no other platform module. `@/lib/db`, the hook system, `@/lib/apps/env` and the push sender are each a capability without its declaration; use `context`. Types may come from anywhere. An import is judged by the file it lands on, so a relative path into `src/` or another app is refused even when it spells a module on the list, and so is a runtime import of a connector or another app. Code loads no other way: `require`, `module`, an `import()` of anything but the app's own file by a literal, `import.meta`, and code in a dot-directory or `assets/` are refused, and so are symlinks, `node_modules/` and `package.json` anywhere in the app. `callAppRoute` takes the app's own slug as a string literal, and nothing imported from outside the app may be written to. All of it fails the build, not just lint: the registry generator checks every app on every build and every Registry install, and skips one that breaks a rule, naming the file and line. There is no escape hatch. A helper apps need is added for every app by a reviewed change to the policy, or becomes a `context` capability. See [`docs/security-architecture.md` §24](../docs/security-architecture.md#24-environment-containment).

32. **A component taken from another app comes in through `/mixos remix`, and its `remixedFrom` entry is never edited.** The remix records the moment it was taken — the source app, the exact commit, what was kept, changed and removed — and the creator of the source sees it once your app is published. Change the remixed code freely; never change the entry. The pre-commit hook and the pull-request checks refuse an edit, and remixing again from a newer version is a new entry. A remixed component never imports, links to or calls the app it came from, and every file the remix wrote keeps the credit comment at its top: the source app, its version, its authors and the day. See [`docs/apps/remix.md`](../docs/apps/remix.md).

33. **Release notes are one line each, in `release-notes.json` beside `app.json`, never in the manifest.** The file is `{ "$schema", "notes": [...] }`, newest first, each note `{ "date", "version"?, "note" }`: `date` the day the change shipped (`YYYY-MM-DD`, no later than tomorrow), `version` three numbers when there is one, and `note` one line of plain text of 300 characters or fewer, no Markdown. Add one with every change a person using the app would notice, written for that person rather than a developer, and the first one says what the app does. The menu bar shows each person the last 14 days' notes for the apps they installed, and App Manager's Release Notes page all of them. The build and a Registry install check the file and refuse one that breaks a rule. See [`docs/apps/architecture.md`](../docs/apps/architecture.md#release-notes-release-notesjson).

34. **Every JSON file starts with `$schema`, which says which shape it is.** `app.json` starts `"$schema": "https://mixos.org/schemas/app/v1.json"`, and `release-notes.json` `"$schema": "https://mixos.org/schemas/release-notes/v1.json"`. The build and a Registry install refuse a file without it, or naming a version this MixOS doesn't read: a newer one needs a newer MixOS, and an older one is a shape it no longer reads. Start from the template, which carries both; the pre-commit hook adds `$schema` to a manifest that has none, and never changes one that has it. `.registry.json` carries one too, written by install. mixos.org sets each release's minimum MixOS version from it. See [`$schema`](../docs/apps/architecture.md#schema-which-shape-a-file-is).

Authoritative types: [`src/lib/apps/types.ts`](../src/lib/apps/types.ts). Canonical template: [`apps/_template/`](_template/).

## Verify (run these before reporting done)

From the repo root:

1. `npx tsx scripts/generate-project-registry.ts` — regenerates `src/generated/app-registry.ts`. Confirm your app appears with the expected widgets **and routes**. Before it loads any of your code, the generator reads all of it and skips the app, naming each file and line, if the code reaches what an app may not (invariants 25, 28 and 31). The generator imports every `api/**/route.ts`: a bare handler export, a JSON route with no `output`, a route file exporting no HTTP method, or a role your app never declared each abort the build. The generator **schema-validates `app.json`** (via `scripts/manifest-schemas.ts`): an unknown field, a wrong-typed value, a bad `defaultRole`, or an auto-generated field set by hand **aborts the whole build** with a message pointing at the offending path. Keep the manifest within the fields in `src/lib/apps/types.ts`. A Registry install runs the same checks on its download and runs none of your code: the app waits in `.mixos/pending/apps/<slug>/` until someone registers it in their checkout: **Review and register** on Admin > Apps, which first shows what will run, or `npm run register -- app/<slug>`. Either moves it into `apps/` and runs this generator. That run is the first time any of your code executes there. Install reads each route's `defineRoute({...})` options from the source, so a bare handler, an undeclared role or `raw: true` without its escape is refused there too, in the same words. Options it can't read as written (built from a variable, a spread, a call or another file), the rest of each route's contract, and `widgets.ts` are checked at Register, by the run that imports them. A refusal there puts the app back in pending. Register also refuses a pending copy whose files changed after install, so what runs is exactly the release that was checked. A newer release of an installed app is an update: **Update** on its notice or its Browse listing downloads it to pending with a record of what it replaces, and Register swaps it for the folder in `apps/`, keeping the old folder in `.mixos/backup/` until this generator accepts the new one, and putting it back if it doesn't. It refuses a folder that changed after the update was prepared. The app's activation, grants and settings carry over; new migrations are applied by `npm run migrate:apps`. Register hands back the change to commit and how to roll it back. Install writes `.registry.json` into the app's folder, which says where it came from and what was verified; it is committed with the app, and never written by hand. Edit an installed app and the generator marks it modified locally. To make it your own, delete its `.registry.json`, and it is a local app from then on; the next release step counts that as a different extension (invariant 1).
2. `npm run typecheck` — catches manifest/type drift.
3. If you changed `"database": true` or added migrations: `npm run migrate`.
4. For UI changes, load `/apps/<slug>` in the dev server and exercise the golden path plus one edge case. Don't claim "done" on a UI change you haven't opened in a browser.
5. Run `npx tsx scripts/smoke-test-app.ts <slug>` against the running server, signed in as a user the app is granted to: `SMOKE_EMAIL` and `SMOKE_PASSWORD`, or `SMOKE_COOKIE` (see the script header). It must exit 0. For an app installed from the Registry, `npm run register -- app/<slug> --smoke` registers it and does the rest: migrations, activation, a grant to that user, and this script, on a local database only. See the failure-triage section in [`.claude/skills/mixos/actions/app.md`](../.claude/skills/mixos/actions/app.md).
6. If `app.json` declares `mcp` tools, run `npx @modelcontextprotocol/inspector` against `http://localhost:3000/api/mcp`, complete the OAuth flow, and **call each tool with real arguments**. Read the result as if you were the model: is it answerable, and is anything in there noise? See [`docs/apps/mcp.md`](../docs/apps/mcp.md#verify).
7. If `app.json` declares `schedules`, or the app caches connector/warehouse data, run `npx tsx scripts/run-scheduled-jobs.ts` **twice**. At `/admin/scheduled-jobs`, confirm both runs are `ok` with a duration well under 240s, and that the **second run did materially less work than the first** — the log line should show a smaller window, fewer pages, or fewer items. A second run that costs the same as the first is a full refresh wearing a scheduler's clothes; fix it per [`docs/apps/data-freshness.md`](../docs/apps/data-freshness.md). Then load the page and confirm the read path still renders from the snapshot with the upstream connector unconfigured.

## Anti-patterns (do not do these)

- Importing a connector or `context` in a widget or client page.
- Changing a connector to fit this app: a method named for the app, a projection shaped to its mapper, a filter for its screen. Compose the connector's methods in `lib/server/` instead, or add the provider's missing operation to the connector as a mirror of it.
- Declaring a connector without the version the app was built against, or calling a method that changes data without `"access": "write"` on its entry.
- Calling another app's API routes from your app.
- Editing `src/generated/*-registry.ts` by hand.
- Adding fields to `app.json` that aren't in `src/lib/apps/types.ts`.
- Using an `icon` value that isn't a Lucide icon name.
- Shipping a real app under a folder starting with `_`.
- Using non-lowercase or whitespace-bearing folder names.
- Naming a schema other than your own in a migration, or reaching for a trigger, function or `DO` block — the build refuses them; see invariant 8.
- Returning `error.message` or `err.message` directly in API responses — throw, and let the pipeline answer.
- Importing a platform module that isn't on the list, or reaching one by a relative path. The build refuses both; see [What an app can import](../docs/apps/architecture.md#what-an-app-can-import).
- Showing "Loading..." text or a bare spinner while fetching data — use `Skeleton` components that mirror the final layout.
- Fetching user-provided URLs server-side without validating the hostname — block private IP ranges and cloud metadata endpoints to prevent SSRF.
- Calling `Notification`, `navigator.serviceWorker`, or `PushManager` directly, or writing to `public.push_subscriptions` — use `enablePushNotifications()` (client) and `context.notifications.send()` (API route or job) instead.
- Writing anything from an `mcp/` handler, or calling a connector method that mutates. MCP tools are read-only; `ctx.db` blocks writes and a connector method declared `mutates` throws, but a connector method that writes without declaring `mutates` is on you to avoid.
- Declaring more MCP tools than an app needs, or shipping a tool whose `description` doesn't say what it returns and when to use it — that text is all the model gets.
- Duplicating query logic in an `mcp/` handler instead of sharing the builder its API route already uses. The tool and the UI must never quote different numbers.
- Persisting a provider pagination cursor in your state table between job runs — it will have expired by the next tick. Use a date window instead.
- Bounding a job by item count instead of a wall-clock deadline, or checking the budget only at the top of the run instead of at every boundary.
- Overwriting a good snapshot with an empty upstream result, or reporting a missing snapshot as zeros rather than as unknown.
- An unbounded `delete()` before re-inserting a window's worth of rows — scope it to the window you actually refetched, or a shallow sync will erase a deep backfill.
- Calling a connector on the request path for data a scheduled job could have materialized, or triggering a cache rebuild from an `mcp/` handler instead of serving what's cached and reporting its age.
