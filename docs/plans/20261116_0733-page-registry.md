# Page registry: a new app's page without a restart

**Status:** built on 16 November 2026, on branch `fix/page-registry`. `npm test`, `npm run
typecheck` and `npm run lint` pass, and so does the live check under Verification, on the host and
in the Docker dev container.

**Scope:** platform. One setting in `next.config.ts` and a test that keeps it there.

## Context

The live check of `20261116_0020-route-loaders.md`, on branch `fix/route-loaders`, found that after `npm run new` and `npm run registry` the new app's page,
`/apps/<slug>`, stayed a 404 until `next dev` restarted, even though its API route answered. The
page's server component read an `appRegistry` from `@/generated/app-registry` with only the app
that was there at startup. The gateway, on the same server, read the new one. Rewriting the
registry and recompiling `page.tsx` didn't help. An earlier report said a new app's page worked in
the Docker dev container.

### Reproduced on `main`

On `main` at `e1773bf` (Next 16.4.3, Turbopack), against a scratch Postgres:

1. Start the dev server.
2. Sign in and request `/` and Wall·E's route `GET /api/apps/wall-e-345e113c/quote`. This compiles
   the dashboard and the gateway, but not `/apps/[appSlug]/[[...path]]`.
3. Run `npm run new -- app <name>`, `npm run registry` and `npm run migrate:apps`. Activate the app
   and grant it to the admin.
4. Request `/apps/<slug>` three times.

| Where | Step 4 |
|---|---|
| Host, `npm run dev` | 404, 404, 404 |
| Docker dev container (`app-dev`, source bind-mounted) | 404, 404, 404 |

So it isn't the environment. It's the order of requests. Two variations explain the earlier
reports:

- **The page route compiled before the change.** Request any `/apps/<slug>` before step 3, and
  step 4 answers 200. In the container, a second new app added after the first one's page had
  compiled rendered at once. The first, stale app recovered along with it.
- **A route compiled before the change is requested afterwards.** A request to `/`, or the
  `GET /login` that `npm run dev`'s readiness check sends, makes the stale page render 200.

So whether a new app's page works without a restart depends on what was opened since the server
started. A report of "it works in Docker" and another of "it needs a restart" can both be right.

## Cause

This is a bug in Next 16.4's **server Fast Refresh**. It is on by default for App Router routes
under Turbopack (`experimental.turbopackServerFastRefresh`, or `--no-server-fast-refresh` to turn
it off). It isn't the watcher, gitignore, or how `app-registry.ts` is imported. The rewrite is seen
(`✓ Compiled`), and the chunks written to `.next/dev/server/chunks/` contain the new slug. The
stale copy is the one in memory.

- **One module system for every route.** In dev, the server modules of all App Router routes share
  one Turbopack runtime. Each module is keyed by its path and layer, such as
  `[project]/src/generated/app-registry.ts [app-rsc]`. The dashboard, `/login`, the admin pages and
  `/apps/[appSlug]/[[...path]]` all import that one module.
- **Updates are pulled per route, against that route's last version.** Since 16.4, Next applies a
  server edit only when a request builds a route. It asks Turbopack for an update to that route's
  entries since the version it last pulled for the same route (`setupServerHmr` in
  `next/dist/server/dev/hot-reloader-turbopack.js`, a `versions` map keyed by entry paths). 16.3.8
  subscribed once for the whole project and applied each update as it happened.
- **A route's first pull applies nothing.** With no version to diff against, it returns `none` and
  records a baseline.
- **Loading a route's chunks doesn't replace a loaded module.** The runtime's
  `installCompressedModuleFactories` installs a factory only for a module id that has none, and
  the evaluated module stays in the module cache.

Put together:

1. `/` loads `app-registry.ts [app-rsc]` with the apps there at startup.
2. `npm run registry` rewrites it.
3. The new app's page is the first request to `/apps/[appSlug]/[[...path]]`. That route's chunks on
   disk have the new registry, but the runtime keeps the module `/` loaded, and the route's first
   pull is `none`. The page reads the old registry, doesn't find the app and calls `notFound()`.
4. Each later pull for that route diffs against a baseline that already has the new registry, so
   it never gets the update.
5. Editing `page.tsx` sends an update with `page.tsx` alone. The re-evaluated page imports the same
   stale registry.
6. It recovers when a route whose baseline is older than the rewrite is built again. That route's
   pull includes the registry, and the update replaces the shared module.

Next's own pulls, logged during the reproduction:

| Request | Baseline | Update |
|---|---|---|
| `/apps/<slug>` (first time, after the rewrite) | none | `none` |
| `/apps/<slug>` again | yes | `none` |
| `/apps/<slug>` after a comment-only edit to `page.tsx` | yes | `partial`: `page.tsx [app-rsc]` only (still 404) |
| `/` (compiled before the rewrite) | yes | `partial`: `app-registry.ts [app-rsc]` and `[app-ssr]` |
| `/apps/<slug>` after that | yes | `none`, and it renders 200 |

Two things the route-loaders check saw follow from this:

- **The gateway read the new registry.** It had compiled before the rewrite, from a request to
  Wall·E's route, so its pull included the update.
- **`pageLoaders` was never stale.** Only the app page imports `app-page-loaders.ts`. No other
  route had loaded it, so the page's first load installed the new one.

Nothing in this is specific to generated files. A module shared by two routes, edited, and then
reached first through a route that hadn't compiled yet, is stale the same way. MixOS runs into it
often for two reasons. `npm run registry` rewrites modules that nearly every route imports. And
what you open next is usually a route that hasn't compiled yet: the new app's page.

The bug is still there in Next 16.4.6, the latest release: the same reproduction gives 404 three
times. `16.5.0-canary.52` has the same per-route baseline code.

## Decisions

1. **Turn server Fast Refresh off in `next.config.ts`:** `experimental.turbopackServerFastRefresh:
   false`. It's Next's documented switch. After a change, a route's server chunks are evicted from
   `require.cache`, along with Turbopack's chunk cache, and loaded again, as before Fast Refresh.
   It's in `next.config.ts`, not a flag in `scripts/dev.ts`, so it covers every way of starting
   `next dev`: on the host, in the container, and plain `next dev`.
2. **The cost is accepted.** A server edit re-evaluates the route's server modules rather than only
   the module that changed. The platform already keeps on `globalThis` what has to survive a
   re-evaluation, such as the database pool in `src/lib/db/client.ts`. A page that's right after
   `npm run registry` is worth more than a faster reload.
3. **No workaround in the registry.** Reading the registry from disk on each request, or touching a
   file that forces Next into a full reload, would only cover generated files, and the bug isn't
   limited to them.
4. **Remove the setting once Next fixes it.** To check, run the reproduction under Verification on
   a new Next with the setting removed.

## Structure

- `next.config.ts`: `experimental.turbopackServerFastRefresh: false`, with the cause in the
  comment.
- `scripts/next-config.test.ts` (new): the setting is `false`.

## Tests

- `scripts/next-config.test.ts`: the config turns server Fast Refresh off. Testing the effect needs
  a running `next dev`, which `npm test` doesn't start, so the live check covers that and the test
  keeps the setting from being removed by accident.

## Verification

- `npm test` (against a throwaway Postgres 17 named by `MIXOS_TEST_DATABASE_URL`), `npm run
  typecheck`, `npm run lint`.
- Live, with the reproduction under Context, on the host (`npm run dev`) and in the Docker dev
  container (`app-dev` through compose, with its own project name and port, the source
  bind-mounted and `DATABASE_URL` pointed at the scratch Postgres):

| | Before (`main`) | After |
|---|---|---|
| Host | 404, 404, 404 | 200, 200, 200 |
| Docker dev container | 404, 404, 404 | 200, 200, 200 |

  With the setting, Next's startup banner lists `⨯ turbopackServerFastRefresh` under Experiments.
  An edit to the new app's `pages/Main.tsx` showed up on the next request, so ordinary server edits
  still reach the page.
- `--no-server-fast-refresh` on `main`, with no config change, gave 200 three times as well. That
  confirms the cause.

## Follow-ups

- Report it to Next.js (`vercel/next.js`), with the reproduction and the table of pulls above: a
  route first built after a shared module changed never gets that change under server Fast
  Refresh.
- When upgrading Next, rerun the reproduction without the setting, and remove it once the page
  renders.
