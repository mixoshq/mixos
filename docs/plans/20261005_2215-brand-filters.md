# Brand filters: the name and marks on the menu bar and sign-in page

**Status:** done, including the stability pass below — verified signed out and signed in
**Scope:** platform — `src/lib/hooks/`, `src/lib/branding/` (new), `src/lib/themes/`, `src/lib/apps/types.ts`, `scripts/`, `src/proxy.ts`, `src/app/layout.tsx`, `src/app/manifest.ts`, `src/app/(main)/layout.tsx`, `src/app/(auth)/login/`, `src/components/header*.tsx`, `src/components/login-lockup.tsx`, `src/components/onboarding/welcome-tour.tsx`, `src/components/admin/app-details-dialog.tsx`, docs

## Context

The product name and its marks are hardcoded. "MixOS" is a literal in the menu
bar (`src/components/header.tsx`), the sign-in lockup
(`src/components/login-lockup.tsx`), the tab title (`src/app/layout.tsx`), the
PWA manifest (`src/app/manifest.ts`) and the welcome tour's copy. The one mark
that is configurable, `assets.logo`, comes from the active theme and is drawn
at two fixed sizes (24×23 in the bar, 72×69 on the sign-in page), so any mark
that is not roughly square is squashed.

[`TRADEMARK.md`](../../TRADEMARK.md) asks a fork to replace the logo and
wordmark in the interface. Today that means editing `src/`.

This makes the three values — **brand name**, **menu-bar logo**, **login logo**
— filterable by apps and declarable by themes, without either touching `src/`.

### What exists today

- **The hook bus has no loader.** Listeners register as an import side effect,
  and nothing imports an app module on `/login` or in the main layout, so a
  filter registered from app code is never live where these values render. See
  [`20261004_2301-login-extensions.md`](20261004_2301-login-extensions.md),
  "What exists today", for the full list of problems.
- **Active-app gating is process-global** (`hooks.setActiveApps`, overwritten
  per dashboard render with one user's installs). Unusable for a value every
  request renders.
- **Apps have no public asset path.** Theme assets, connector icons and
  screenshots are exempt from the auth redirect (`src/proxy.ts`); nothing an app
  ships is. An app's mark would 302 to `/login` on the sign-in page.
- **CSP `img-src` allows any `https:`.** An unchecked filter could put a remote
  image — a tracking pixel — on the sign-in page.

## Decisions

### Locked with the user

| Decision | Choice |
|---|---|
| What is filterable | Brand name, menu-bar logo, login logo |
| Where the name shows | Menu bar, sign-in page, welcome tour, **tab title** and **PWA install name** |
| Theme vs app | **Theme wins.** A slot the theme declares is final; app filters run only for slots the theme leaves open. |

### Made here

| Decision | Choice | Why |
|---|---|---|
| How a theme takes part | Data, not a filter. Core reads `theme.json` and applies it. | A theme runs no code and should not start to. |
| `assets.logo` | Stays, and becomes the **seed** apps filter — not a claim. | Both `mixos` and `mixos-dark` ship it. Treating it as a claim would mean no app could rebrand while a default theme is active. |
| Theme claim field | New `branding: { name?, menuBarLogo?, loginLogo? }` | `name` is taken (it is the theme's own name). A separate block says "this install is this brand", which is a different statement from "this palette has a mark". |
| Hook names | `brand-name`, `menu-bar-logo`, `login-logo` | Core hooks, never slug-prefixed. |
| Filter kind | **Bounded** (the login-extensions taxonomy). | The sign-in page is the most-phished page. |
| App registration | A declared `apps/<slug>/hooks.ts` entrypoint, loaded once per process by `ensureHooksLoaded()` | The login-extensions plan's §"Hook system changes" 1 — built here first, reused there. |
| Activation | Per dispatch, through `isAppActive()` (instance-wide, request-cached) | Not `setActiveApps`. Branding is per install, not per user. |
| App declaration | `branding: { hooks, reason, logos? }` in `app.json`, shown in the admin app dialog | Rebranding the sign-in page is a capability an admin should see before activating. Same shape as `escapes`: declared, with a reason. |
| App images | `apps/<slug>/branding/`, declared files only, copied to `/branding/apps/<slug>/`, proxy-exempt | Mirrors `screenshots/`. Undeclared drafts never reach a public URL. |

## Design

### Precedence, per slot

```
core default  →  theme assets.logo (logos only)  →  app filters  →  theme branding.* (if declared)
"MixOS" / null                                       by priority     final
```

When the theme declares a slot, its filters are **not run at all** — there is
nothing for them to change, and app code is not executed for nothing.

The login logo is seeded from `assets.logo` too, never from the resolved
menu-bar logo: each slot is independent, so an app that filters only one of them
changes only that one.

### Bounded filter semantics

Each callback is awaited with a 1-second timeout. After each one the platform
re-validates the result and keeps the previous value when it fails:

| Hook | Accepted result | Anything else |
|---|---|---|
| `brand-name` | A string; trimmed; control characters stripped; 1–40 characters | Previous value |
| `menu-bar-logo`, `login-logo` | `null` (no mark); the value it was given, unchanged; or a string naming one of **this app's** declared `branding.logos` (e.g. `"branding/acme.png"`), which the platform resolves to its public URL and measured size | Previous value |

So no filter can introduce a URL the platform did not publish, and no app can
point at another app's file. A throw or timeout logs
`[branding] <slug> <hook>: …` and keeps the previous value. A database failure
while checking activation falls back to the unfiltered value: branding is not
worth a 500 on the sign-in page.

Registrations that do not count:
- made on the bare `hooks` singleton (no slug);
- from an app whose manifest does not declare that hook under `branding.hooks`;
- from an inactive app.

### `apps/<slug>/hooks.ts`

```ts
import type { HookRegistrar } from "@/lib/hooks";

export default function register(hooks: HookRegistrar) {
  hooks.addFilter("brand-name", () => "Acme Workspace");
  hooks.addFilter("menu-bar-logo", () => "branding/acme-mark.png");
}
```

The generator emits a server-only `src/generated/app-hook-loaders.ts`
(`hookLoaders: Record<slug, () => import("@apps/<slug>/hooks")>`), beside
`app-page-loaders.ts`. `ensureHooksLoaded()` imports every entrypoint once per
process and calls it with `hooks.createRegistrar(slug)`. A throwing entrypoint
is logged and skipped; the rest still load.

### `app.json`

```jsonc
"branding": {
  "hooks": ["brand-name", "menu-bar-logo"],
  "reason": "Brands this install as Acme for the Acme rollout.",
  "logos": ["branding/acme-mark.png"]
}
```

Build-enforced:
- `hooks` is a non-empty, duplicate-free subset of the three names.
- `reason` is at least 20 characters (the app `escapes` rule).
- Every hook named in `hooks` has a literal `addFilter("<hook>", …)` in
  `hooks.ts`, and every branding `addFilter` in the app is in `hooks.ts` and is
  declared. Both directions, so the declaration can neither under-report nor go
  stale.
- `logos`: files under `branding/`, `.png`/`.jpg`/`.jpeg`/`.webp` (no SVG, for
  the screenshots reason: served unauthenticated), at most 4, at most 512 KB,
  measured. `logos` without a logo hook in `hooks` is an error.

### `theme.json`

```jsonc
"branding": {
  "name": "Acme Workspace",
  "menuBarLogo": "acme-bar.png",
  "loginLogo": "acme-login.png"
}
```

All optional. Logo paths are relative to `assets/`, like every other theme
asset, and are raster formats that the build measures. `assets.logo` is now
measured too, so it must be `.png`/`.jpg`/`.jpeg`/`.webp`. Both in-repo themes
already comply.

### Rendering

- `getBranding()` (`src/lib/branding/resolve.ts`, React `cache`) returns
  `{ name, menuBarLogo, loginLogo }`, each logo `{ src, width, height } | null`.
- Logos are drawn at a fixed height with width from the measured aspect ratio,
  capped: the bar at 23px high and at most 160px wide, the sign-in page at 69px
  high and at most 240px wide. `next/image` gets those display sizes, so its
  `srcset` is 1x/2x of what is shown.
- A long name truncates in the bar rather than pushing the Dashboard link.
- **Welcome tour.** When the two logos differ, the login mark fades in place
  instead of flying into a different image. The wordmark still flies. The tour
  copy uses the brand name.
- Tab title: `{ default: name, template: "%s | <name>" }`. PWA: `name` and
  `short_name`.

### Admin visibility

The app details dialog's Hooks section lists the branding declaration and its
`reason`. The theme picker is unchanged in this pass.

## Stability pass

Follow-up work after the first cut, in the order it was asked for.

1. **SVG theme logos are accepted again.** The theme docs used to say "SVG,
   ideally", and the first cut broke any theme that followed that advice. The
   build now reads an SVG's size from its root's absolute `width`/`height`, or
   from its `viewBox`, without running it (`readSvgSize` in
   `scripts/image-size.ts`). next/image already serves `.svg` unoptimized. App
   logos stay raster-only.
2. **The order is fixed.** Filters used to run in registration order, which
   depends on import timing and, in development, on which `hooks.ts` was saved
   last. They now run by priority, then by app slug (`eligibleFilters`). When
   more than one active app filters a slot, it is logged and shown as a notice
   on `/admin/apps` (`src/components/admin/brand-conflicts.tsx`). A slot the
   theme claims is not shown, because no app filter runs for it.
3. **The menu-bar mark can shrink.** It keeps its proportions, so a wide
   lockup no longer spills over the Dashboard link on a phone.
4. **Each slot has its own getter and one budget.** `getBrandName`,
   `getMenuBarLogo` and `getLoginLogo` replace `getBranding`, so a page runs
   only the filters it draws. The main layout asks for the sign-in mark only
   while the tour is showing. A slot's filters share one 1s budget, so slow
   apps add up to at most one second.
5. **The last good value is kept, and each problem is logged once.** A run in
   which any filter fails serves the last clean value for the same theme,
   scheduled apps and hook generation (`LastGood`). The generation is bumped
   whenever a `hooks.ts` reloads, so an edited filter never shows a stale
   value. Activation is one query that throws on error instead of reading as
   "inactive", so a database blip also serves the last good value rather than
   "MixOS".
6. **Tests.** `npm test` runs Node's built-in test runner through `tsx --test`.
   No dependency was added. CI runs it after typecheck. Everything tested is
   free of the database and of generated files. The dispatch rules live in
   `src/lib/branding/bounded.ts`, and the generator's brand checks in
   `scripts/brand-checks.ts`, which is tested against fixture folders.
   `FatalManifestError` moved to `scripts/manifest-errors.ts`, so an error
   thrown from an extracted check still aborts the build.

Verified in a browser, signed in as the seeded admin:
- **Menu bar at 1280px and 375px with an 8:1 mark.** It is capped at 160×20 on
  desktop and shrinks to 68×8.5 on a phone, with the name truncated and no
  overlap.
- **Welcome tour.**
  - With differing marks, the sign-in mark fades in place and the wordmark
    lands within 0.4px.
  - With matching marks, the mark lands within 0.6px.
- **Conflict notice.** It renders on `/admin/apps`.

Verified against the dev server:
- **Fixed winner.** With two apps competing, the winner was the same on every
  request.
- **Last good value.** A filter that hangs every other call still showed the
  last good name.
- **Only the filters the page needs.** `/login` answered in about 50ms while a
  menu-bar filter hung permanently.
- **Logging.** Each problem was logged once.
- **SVG theme logo.** One with only a `viewBox` measured 300×100 and was drawn
  at 207×69.
