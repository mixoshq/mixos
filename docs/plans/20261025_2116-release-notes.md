# Release notes in the menu bar

## Context

Nothing in MixOS tells the people using it what changed. `CHANGELOG.md` and
`WHATS-NEW.md` are written for developers and admins, and an extension has no
place to say anything at all: an app gains a page, a connector a method, a
theme a new ground, and the people who use them find out by noticing.

So every app, connector and theme, and MixOS itself, keeps short release
notes, one line each, and the menu bar shows the new ones to each person, for
the extensions in their own workspace.

## Decisions (locked with the user)

- **A file of its own, not the manifest.** The Release Notes page keeps the
  full history, so notes accumulate with every release, and a manifest that
  grew a changelog would be mostly changelog. Each extension keeps
  `release-notes.json` beside its manifest; MixOS keeps one at the repository
  root.
- **One line each, 300 characters or fewer.** `[{ "date", "version"?, "note" }]`,
  newest first. `note` is plain text on one line. `date` is the day the change
  shipped, `YYYY-MM-DD`. `version` is optional: a connector has one, an app or
  theme release is named by its tag.
- **What is "new":** every note dated within the last 14 days (its date and the
  13 days after). Nothing in that window: no icon at all.
- **Whose notes:** MixOS's, and the extensions that are on in the person's
  workspace: the apps they installed in App Manager and still hold (active, and
  granted or global), the connectors not switched off, and the active theme.
- **The icon:** a gift, before the name dropdown, with a red count of the notes
  not yet seen. Each unseen note has a red dot, which goes once the pointer has
  rested on it for a second, or, on a device without hover, once it has been on
  screen for a second. Seen state is per person, in the database. When all are
  seen the icon stays, without a count, until the window passes.
- **The popover:** headed "What's new", with the gift before it, on the menu
  bar's own colour. MixOS's notes first, under its name, with no heading over
  them; then a section each for Apps, Connectors and Themes, the notes grouped
  by extension. An app with pages gets **Go to App**. At the bottom, **See all
  release notes**.
- **The page:** App Manager gets a **Release Notes** button, top right, to
  `/apps/release-notes`, nested under App Manager. It lists every note for the
  same extensions, newest first, with a filter: All, MixOS Core, then Apps,
  Connectors and Themes, each selectable whole or one extension at a time.
- **Back-dated notes** for the existing extensions: Wall-E and the two built-in
  themes here, and each extension repository, each in a pull request of its own.
  MixOS itself is not back-dated; its first note is this feature.

## Structure

### The file, and the build

- `src/lib/release-notes/types.ts`: the file name, the limits, the window, and
  `ReleaseNote`, the generated entry. No server-only imports, so the generator
  and client components can read it.
- `scripts/release-notes.ts`: reads and validates one `release-notes.json`.
  Strict objects, a real date no later than tomorrow (a typo'd year would pin a
  note as new for a year), one line, trimmed, 1 to 300 characters counted as a
  person counts them, a dotted version, newest first, no duplicates, 256 KB at
  most. A missing file is no notes. Each note gets a stable id,
  `<kind>:<slug>:<date>:<hash of its text>`: editing a note's text makes it new
  again.
- `scripts/generate-project-registry.ts`:
  - `readAppText()`, `readConnector()` and `readTheme()` validate the file, so
    an install's `--check` refuses a bad one before it lands, and a build aborts
    on one, as for a bad manifest.
  - `main()` collects the notes of what was accepted, and MixOS's from the root,
    into `src/generated/release-notes.ts`. Server only: the client gets a
    person's notes from a server action, never the whole file.
  - An app may not be called `release-notes`, which is the page's URL under
    `/apps` (`RESERVED_APP_SLUGS` in `src/lib/apps/app-identifiers.ts`).

### Seen state

- `supabase/migrations/0002_release_notes_seen.sql`: `release_notes_seen
  (user_id, note_id, note_date, seen_at)`, keyed by person and note, deleted
  with the person, RLS on with no policies, and `platform_schema_version` 2.
  Marking prunes the person's rows for notes older than the window, so the table
  holds at most one window of notes per person.

### Runtime

- `src/lib/release-notes/select.ts`: pure. The window, which notes a workspace
  shows, and the grouping and order both surfaces use.
- `src/lib/release-notes/server.ts`: a person's workspace (`getUserApps()`,
  `getDisabledConnectors()`, `getActiveTheme()`), their notes, and the seen
  rows.
- `src/lib/release-notes/actions.ts`: `getMyRecentReleaseNotes()` and
  `markMyReleaseNotesSeen(ids)`. Marking accepts only the ids of notes the
  person can see now, and revalidates nothing, so a page doesn't re-render on a
  hover.
- `src/components/release-notes/release-notes-menu.tsx`: the icon, the count
  and the popover. Loads on mount, again on open and when an app is installed,
  and sends marks in batches.
- `src/components/release-notes/release-notes-browser.tsx`: the page's filter
  (in the URL, `?show=`) and list.
- `src/app/(main)/apps/release-notes/page.tsx`, and the button in
  `src/app/(main)/apps/page.tsx`.

### Docs and skills

- `docs/apps/architecture.md`, `docs/connectors/architecture.md`,
  `docs/themes/architecture.md`: the file and its rules.
- `apps/AGENTS.md`, `connectors/AGENTS.md`, `themes/AGENTS.md`: an invariant
  each.
- `/mixos app`, `connector`, `theme` and `convert`: write the note with the
  change. `/mixos deploy`: draft one for a change that has none.
- `WHATS-NEW.md`, and `docs/security-architecture.md`'s table list.

## Verification

- `npm test`: the file's rules (`scripts/release-notes.test.ts`), the window
  and grouping (`src/lib/release-notes/select.test.ts`), the reserved slug.
- `npm run registry`: the notes are collected; a bad file aborts the run and an
  install's `--check` rejects it.
- `npm run typecheck`, `npm run lint`.
- `npm run db:migrate` on the local stack, then in the browser: the icon and
  count, a dot clearing after a second's hover, the count going down, a reload
  keeping them seen, Go to App, See all, App Manager's button, the filter and its
  URL, a narrow window, and no icon when nothing is in the window.
