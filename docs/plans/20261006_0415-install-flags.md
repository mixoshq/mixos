# Install flags: fixing what an instance runs

## Context

An admin can browse the catalogue at mixos.org from the Apps, Connectors and
Themes admin pages and install from it (docs/security-architecture.md §31). Some
instances want what runs to be decided in code review and shipped in the build,
not by whoever holds an admin account. The ask: `INSTALL_APPS`,
`INSTALL_CONNECTORS` and `INSTALL_THEMES`, default `true`; with one `false`,
there is no way to reach that kind's browse page or to install that kind.

## Decisions

- **Install means the catalogue path only.** In this codebase *Install* is
  catalogue → instance; *Activate* and *Enable* are later stages
  (docs/plans/20260923_0230-app-activation.md). The flags leave those alone, and
  leave already-installed extensions alone.
- **Close the path, not just the link.** Server actions are directly invocable,
  so hiding the button and the page would leave installing open to a crafted
  request. Each layer checks for itself: the button, the page (404, after the
  admin gate), all three actions, and `installExtension()` before it takes the
  platform lock.
- **A 404, not an explanation page.** With a kind off, its browse page does not
  exist on that instance.
- **Fail closed on unrecognised values.** Unset and empty are on; `true`/`1`/
  `yes`/`on` and `false`/`0`/`no`/`off` in any case; anything else is off, with
  a warning in the log and in the release step's report. A kind that is not one
  of the three is refused outright, and the refusal message is built without
  indexing label maps with untrusted input (`"constructor"` is a key every
  object has).
- **Read per request.** The admin pages render dynamically, so a restart
  applies a change without a rebuild.
- **Not in `render.yaml`.** A value declared in a Blueprint can be re-applied on
  sync over an operator's change in the dashboard, which would silently undo a
  `false`. The flags pass through the Compose stack, where `deploy/.env` is the
  operator's.

## Structure

- `src/lib/repository/policy.ts` — `parseInstallFlag`, `installEnabled`,
  `installFlagProblems`, `installDisabledMessage`; `policy.test.ts`.
- `src/lib/repository/install.ts` — `InstallError` code `"disabled"`;
  `checkInstallable` and `installExtension` refuse a disabled kind.
- `src/lib/repository/actions.ts` — search and resolve refuse a disabled kind;
  register is refused by the pipeline and audited as
  `<kind>.register.rejected`, `reason: "disabled"`.
- `src/components/admin/browse/browse-page.tsx` — `notFound()`.
- `src/app/(main)/admin/{apps,connectors,themes}/page.tsx` — the Browse button
  renders only when the kind is on.
- `scripts/release.ts` — reports unrecognised flag values.
- `deploy/docker-compose.yml`, `deploy/.env.example`, `.env.local.example`.
- Docs: `docs/hosting/README.md` (table and "Fixing what an instance runs"),
  `docs/security-architecture.md` §31 "Turning it off", README, `WHATS-NEW.md`.

## Verification

- Unit tests for parsing, per-kind lookup, unknown kinds, the release report,
  and `installExtension()` refusing before the lock.
- A dev server on a fresh Postgres with `INSTALL_APPS=false`,
  `INSTALL_CONNECTORS=nope` and `INSTALL_THEMES` unset:
  - Apps and connectors had no Browse button, and their browse pages answered
    404. Themes had both, and its catalogue search returned results.
  - The typo was warned once in the server log and reported by the release
    step.
  - Called directly with a `Next-Action` header, search, resolve and register
    all refused the disabled kinds. Register wrote `app.register.rejected` with
    reason `disabled`, and a made-up kind was refused with a clear message.
- `npm run typecheck`, `npm run lint`, `npm test`.
