**Builds on:** [`20261110_0018-slug-ids.md`](20261110_0018-slug-ids.md). This replaces its

## Context

An extension's slug is its folder name, and its name everywhere: URL, database schema and role,
grants, a connector's credentials and OAuth redirect URI, a theme's `data-theme`. Since slug ids,
every listed slug ends in an 8-character id (`careers-83462f9f`), so two extensions with the same
plain name can be installed side by side.

But the id exists only where mixos.org minted it. Extension repositories keep the extension at
their root, so nothing in the repository records it, and:

- **Every first listing fails.** The app's code was written against its plain name
  (`createAppClient("careers")`, `callAppRoute("careers", …)`), and mixos.org's release check
  refuses an app whose code names anything but its listing's slug. The publisher has to rename
  their code and their own folder to an id they have never seen.
- **The id isn't stable.** A deleted draft takes its id with it. Checking the same repository
  again mints a new one, and code renamed to the old id no longer matches. This happened to
  Career: its code names `careers-baa28a1b`, a deleted draft's id, and its new draft is
  `careers-83462f9f`.

So the id moves into the manifest, minted once when the extension is created, and everything
reads it from there.

## Decisions (locked with the owner)

1. **`registryId` is a manifest field in `app.json`, `connector.json` and `theme.json`.** It
   holds the full install name, `"registryId": "careers-83462f9f"`: a base and an 8-hex id. It
   is not a display name. `app.json` `name`, `connector.json` `displayName` and `theme.json`
   `name` stay what people read.
2. **The developer mints it, locally, when the extension is created.** mixos.org stops minting.
   It reads `registryId` and lists the extension under it, if no other repository holds it.
3. **The folder must equal `registryId`.** That is the security goal: no two extensions can
   share a name and id. The build, every install path, and mixos.org each check their part
   (see "How two extensions are kept apart").
4. **Every install uses it.** A Registry install already lands in `<kind>/<listing slug>/`, and
   the listing's slug is now the manifest's `registryId`. An extension copied in by hand, or
   developed in place, builds only in a folder named its `registryId`.
5. **Schema v1 changes in place, with `registryId` required.** No apps, connectors or themes
   exist yet, so there is no v2 and no compatibility path. `since` for app, connector and theme
   v1 goes back to `"unreleased"`, so the next release stamps itself as v1's first reader.
   That release refuses every manifest without `registryId`.
6. **All three kinds**, so one rule covers them all.
7. **On mixos.org, a `registryId` stays with the repository that first listed it**, by kind,
   repository and path. That holds even after its draft is deleted, so a fork has to mint its
   own before it can be listed.

## Owner decisions (recommendations marked)

- **O1. Connectors: `registryId` replaces `connector.json` `name`.** *Recommended.* A
  connector's `name` already is its slug. It must equal the folder today
  (`readConnector`, generator 1886), and it's what apps name in `connectors`,
  `optionalConnectors`, `sync[].source`, `mcp[].sources` and `context.connectors["…"]`. Keeping
  both would mean two fields that must always hold the same value. With no connectors in the
  wild, the field is renamed. Apps' references keep their own `name` key: it names a connector
  by its `registryId`.
  *Alternative:* keep `name`, add `registryId`, and require them equal.
- **O2. `registryId` must end in an id, everywhere.** *Recommended.* The pattern is
  `^[a-z0-9]+(?:-[a-z0-9]+)*-[0-9a-f]{8}$`, 2–48 characters. That is mixos.org's `SLUG_PATTERN`
  and length, and core's install `SlugSchema`, plus the id. It also settles today's three
  slightly different patterns: apps allow `_`, `SlugSchema` doesn't and caps at 48, and themes
  check only `^[a-z0-9][a-z0-9-]*$`.
  The cost is that every test fixture with a plain folder name (`acme`, `crm`, `probe-conn`, …)
  gets an id.
  *Alternative:* only require folder = `registryId`, any slug. That leaves the security goal to
  mixos.org alone.
- **O3. A scaffold script, `npm run new -- <kind> <name>`.** *Recommended.* There is no scaffold
  today: the `/mixos app|connector|theme` actions tell the agent to copy `_template` by hand. The
  script copies the template, mints the id, names the folder `<name>-<id>` and writes
  `registryId`. Minting is then mechanical, and the actions call the script.
  - The templates carry a placeholder, `"registryId": "template-00000000"`. It passes the schema,
    so the template tests still parse them.
  - The build refuses an all-zero id outside `_` folders, so a hand-copied template fails until
    it is minted.
- **O4. The pre-commit stamp fills in `registryId` when it can.** *Recommended.* For a folder
  that already ends in an id and has no `registryId`, `scripts/stamp-updated.ts` inserts
  `registryId` = folder, as it inserts a missing `$schema`.
  - A folder without an id gets no guess. The build error says to run
    `npm run rename -- <kind>/<folder>`, which mints one and (new) writes `registryId`.
  - `/mixos upgrade` does the same for a user's own extensions.
- **O5. Renames stay in the ledger.** *Recommended, no change.* `extension-renames.ts` explains
  why a manifest field can't claim another extension's data. `registryId` claims only its own
  folder's name, which the folder must match, so it changes nothing about renames.
  `npm run rename` moves the folder and rewrites `registryId` with it.

## How two extensions are kept apart

- **On one instance:** a folder has one name, and the build refuses a manifest whose
  `registryId` isn't it. An install refuses a folder that already exists (`install.ts` 1737), and
  an update must match the folder's install record (`recordMismatch`). The release step still
  switches off a new extension that takes a slug the instance already knows.
- **Across the Registry:** mixos.org lists a `registryId` once per kind, and keeps it with the
  repository that first listed it (decision 7). A copied repository can't be listed under the
  original's `registryId`.
- **Between the two:** install's preflight refuses a release whose `registryId` differs from the
  listing's slug. So a release can't land in a folder other than the one its manifest names.

### mixos.org

- **No minting.** Every call site reads `registryId` instead: the publish page (Check and Save),
  the CLI's publish endpoint and `mixos check`. `proposeSlug`, `proposedName` and `remintSlug`
  go; `slug-id.ts` keeps the format checks and adds `registryIdRejection`.
  - `ExtensionRead.installName` (a connector's `name`) becomes `registryId`, read for every kind,
    and judged only by the release check (`registryIdProblem`, `registryIdMismatch`,
    `registryIdUnavailable` in `release-check.ts`), so a manifest without one is still shown.
  - `mixos publish --slug` only picks between the caller's listings; the preview's `slug` field
    and the "choose another name" prompt go, because a taken `registryId` is fixed in the
    repository.
- **A manifest without one** (or with an all-zero id) is a problem with What / Where / How to
  fix: run `npm run new` for a new extension, or `npm run rename -- <kind>/<folder>`, in your
  MixOS checkout, then commit. Copy Fix Prompt carries the same steps.
- **Binding (decision 7):** migration 0024, a `registry_ids` table of kind, `registry_id`,
  repository owner and name (lowercased), path, and the publisher who listed it first.
  - Written by a trigger on `listings`, which binds a slug the first time it is listed and
    refuses a listing whose slug another repository or path holds. So the website, the CLI's API
    and a publisher's own REST writes all bind the same way. No policy lets anyone read or write
    the table; `check_registry_id()`, which the site asks before saving, says `invalid`, `bound`
    or `retired`, never whose.
  - Bindings outlive the listing, so a deleted draft's name stays with its repository.
  - Keyed by owner/name, as listings are, not by GitHub's numeric id: mixos.org stores no
    numeric id, so existing listings couldn't be backfilled with one. A renamed repository is a
    new one to the binding, as it already is to its listings.
  - Backfilled from every listing whose slug carries an id.
- **Existing drafts:** a draft whose slug differs from its manifest's `registryId` says so.
  Slugs never change, so the fix is to delete the draft and check again.
- **`slug-references`** stays as it is: code must name the listing's slug, which is now the
  manifest's `registryId`.
- **Schemas:** `npm run sync:docs` after the MixOS release. Until then the index calls v1
  unreleased, and mixos.org refuses every listing. After it, every listing's Requires MixOS is
  that release.

## Deploy order

Merge PR 1 and cut the MixOS release; it stamps v1's `since`. Then PR 2 on mixos.org, with
`npm run sync:docs`. If mixos.org syncs earlier, it refuses every listing until the release.
With no extensions, nothing is cut off in between.
