# Route loaders: one explicit import per app route

**Status:** built on 16 November 2026, on branch `fix/route-loaders`. All of these pass:
`npm test` (1963 tests against a throwaway Postgres 17; 1679 pass and 14 are skipped without
one), `npm run typecheck`, `npm run lint` and the live check under Verification.

**Scope:** platform. The registry generator (`scripts/generate-project-registry.ts`, plus a new
`scripts/route-loaders.ts`), a new generated file `src/generated/app-route-loaders.ts`, its one
consumer `src/lib/apps/route-loader.ts`, the gateway (`src/lib/apps/dispatch.ts`),
`callAppRoute` (`src/lib/apps/call.ts`), and the comment in `next.config.ts` that lists routes
among the template-literal imports.

## Context

If you create an app while `next dev` is running, its pages work but every API route answers 404
until the server restarts. The log says:

```
[gateway] <slug>/api/<path> failed to load: Error: Cannot find module '@apps/<slug>/api/<path>/route'
```

Both the gateway and `callAppRoute` load a route with a template-literal import:

```ts
mod = await import(`@apps/${appSlug}/api/${routePath}/route`);
```

Turbopack turns a template import into a context of the files that match it on disk when the
importing module compiles. A folder added under `apps/` later isn't in that context, and nothing
recompiles `dispatch.ts` or `call.ts` to refresh it. So the import fails, the `catch` logs it, and
the gateway answers 404.

Pages don't have this problem. The generator writes `src/generated/app-page-loaders.ts`, which has
one explicit `import("@apps/<slug>/pages/…")` per page. `npm run registry` rewrites that file, Next
recompiles it, and the new page's import is in the graph.

## Decisions

1. **The same pattern as pages.** The generator writes `src/generated/app-route-loaders.ts`: a
   `routeLoaders` map keyed `<slug>/api/<modulePath>/route`, with one explicit
   `import("@apps/<slug>/api/<modulePath>/route")` per route file. `<modulePath>` is the on-disk
   path, `index` for the root route, with dynamic segments kept (`items/[id]`). The key spells out
   the import specifier, so a log line names the file. The map is built from each registered app's
   hoisted `routes`, so it contains exactly the routes the registry vouches for. A rejected app
   gets no loaders.
2. **Server only, in its own file.** The map follows the same NOTE as `pageLoaders` and
   `hookLoaders`. It lives apart from `app-registry.ts`, which client components import, so no app
   route module enters the client graph. Its one consumer is `src/lib/apps/route-loader.ts`.
3. **One loader, used by both callers.** `loadRouteModule(slug, modulePath)` returns one of three
   results: `loaded` (with the module), `missing` (no entry in the map), or `failed` (the module
   threw while loading, with the error). The gateway and `callAppRoute` both use it. Neither builds
   the key itself.
4. **"Missing" and "throws at load" stay apart.** The gateway's step 6 keeps the import separate
   from dispatch, as before. Neither case changes what the caller sees:
   - The gateway answers 404 for both, as today. `callAppRoute` throws `NOT_FOUND` with the same
     message as today.
   - What changes is the log. A missing loader warns that the route is on disk but not in the
     generated map, and says to run `npm run registry`. A throwing module logs `failed to load`
     with the error, as today.

   Before, a missing module and a module that threw at its top level produced the same "failed to
   load" line.
5. **Lookups by own key only.** The lookup uses `Object.hasOwn`, so no key can reach a prototype
   property. The slug is already checked against `appRegistry` and the path comes from a directory
   listing or the hoisted contract, so this is a second line of defence, not the first.
6. **Only routes change in this PR.** MCP tools (`src/lib/mcp/tools.ts`), syncs and jobs
   (`src/lib/apps/scheduler.ts`), services (`src/lib/apps/services.ts`) and connectors use the same
   template-literal import and probably have the same restart bug. They stay as they are here and
   are listed as follow-ups.

## Structure

- `src/lib/apps/route-modules.ts` (new). Pure, with no generated import, so both the generator and
  the runtime can use it:
  - `routeModulePath(path)` maps `""` to `"index"`.
  - `routeLoaderKey(slug, modulePath)` builds the key.

  The generator already imports from `src/lib/`, so the two sides share one key rule.
- `scripts/route-loaders.ts` (new). Pure, no I/O: `routeLoadersSource(apps)` returns the generated
  file's text, built from `{ slug, routes }[]`.
- `scripts/generate-project-registry.ts`: writes `APP_ROUTE_LOADERS_FILE` next to the page and hook
  loaders, from `apps`. The typed client surface uses `routeModulePath` too, so there is one rule
  for `index`.
- `src/generated/app-route-loaders.ts` (generated, gitignored like the rest of `src/generated/`):
  `export const routeLoaders: Record<string, () => Promise<Record<string, unknown>>>`.
- `src/lib/apps/route-loader.ts` (new): `loadRouteModule`, the map's one consumer.
- `src/lib/apps/dispatch.ts` step 6 and `src/lib/apps/call.ts`: replace the template import with
  `loadRouteModule`. The comments explain why.
- `next.config.ts`: drop routes from the comment's list of template imports, and say that the
  route map now pulls routes into the bundle.
- The two database-backed suites (`app-gate.integration.test.ts`,
  `app-maintenance.integration.test.ts`) add their fixture routes to `routeLoaders`, as they already
  do for `hookLoaders` and `pageLoaders`.

## Tests

- `scripts/route-loaders.test.ts`:
  - The generated text has one explicit `import("@apps/…/route")` per route, with the right keys
    (index, nested, `[id]`, `[...rest]`). It has no template literal, and an app without routes
    gets nothing.
  - Through `scanApps` on a fixture app, every `route.ts` on disk gets exactly one entry.
  - The generated file, written out and imported with `@apps/` pointed at the fixture, loads each
    route module.
- `src/lib/apps/route-loader.test.ts`:
  - `loadRouteModule` returns `missing`, `failed` and `loaded`, and doesn't resolve prototype keys.
  - Through the real gateway and `callAppRoute`, with the maintenance state, the app gate, the rate
    limiter and the router stubbed:
    - A route with no loader is a 404 / `NOT_FOUND` with the "run `npm run registry`" warning.
    - A loader that throws is a 404 / `NOT_FOUND` with "failed to load" and the error.
    - A loaded module reaches method lookup: 405 for a method it doesn't export, and
      `HANDLER_ERROR` for a non-`defineRoute` export.

## Verification

- `npm test`, `npm run typecheck`, `npm run lint`.
- The database-backed suites against a throwaway Postgres (`MIXOS_TEST_DATABASE_URL`), since they
  exercise both callers end to end.
- Live:
  1. Start `npm run dev`.
  2. Run `npm run new -- app <name>`, then `npm run registry`.
  3. Request the new app's route and confirm it answers without a restart. Before the fix, the same
     sequence returns 404.
  4. Remove the scratch app afterwards.

What the live check found, on a second `npm run dev` (port 3005) against a scratch database:

- `npm run new -- app loadercheck` and then `npm run registry` ran while the server was up. The
  gateway had already compiled, from a request to `wall-e`'s route.
- After the app was activated and the admin granted it, `GET /api/apps/loadercheck-913a985d/hello`
  returned 200 `{"message":"HELLO, ADMIN!"}` with no restart (one `Ready` in the log).
- Before the grant, the same request returned 401 and then 403. Both answers come after the route
  module has loaded.
- The server logged no `[gateway]` lines.
- After a restart, the app's page rendered through `callAppRoute` and the map.

## Follow-ups

- The same explicit-loader map for MCP tools, search handlers, syncs, jobs and services. Each
  has the same template-literal import and probably the same "works after a restart" bug. Done in
  [`20261116_0722-extension-loaders.md`](20261116_0722-extension-loaders.md).
- **A new app's page needed a restart in the live check.** The page's server component still read
  the `appRegistry` from before `npm run registry`, with only `wall-e` in it. The gateway, on the
  same server, read the new one. So `/apps/<slug>` was a 404 until the restart. Rewriting the
  registry again and recompiling the page didn't help. This happens before any route loading,
  so this fix doesn't cause it. It wasn't checked against `main` or inside the Docker dev
  container, where pages of a new app were seen to work.
