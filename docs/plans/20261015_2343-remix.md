# Remix: bring a component from one installed app into another

**Status:** every decision settled with the owner on 15 October 2026. All three phases built on 16 October 2026: phases 1 and 2 here, phase 3 in the mixos.org repository. See [As built](#as-built).
**Scope:** platform — `.claude/skills/mixos/actions/remix.md` (new), `scripts/manifest-schemas.ts`, `scripts/generate-project-registry.ts`, `src/components/admin/app-details-dialog.tsx`, `docs/apps/remix.md` (new); and, in the mixos.org repository, ingest and the creator view.

## Context

A developer sees a component in one app — a table, a widget, a layout — and wants
it in their own app. Today that means reading the other app's code and rebuilding
it by hand, and nobody learns that the component was worth taking.

Remix makes that an agent action. The developer points at a component in an app
installed on the instance. The agent abstracts it into a **remix card**: the data
it needs, what it gives back, and every action it takes. The developer decides,
action by action, whether it does the same thing in their app, something
different, or nothing. The agent writes a plan, stops for approval, then builds
the component inside the target app and records where it came from.

That record is what feeds the second half: once a remix is merged into an app
that is published on mixos.org, the source app's creator sees which parts of
their app were remixed, how often, and what people kept, changed and removed.

## Decisions

Settled with the owner on 11–15 October 2026.

## The remix card

What the agent extracts, shows the developer, and writes into the plan. Five parts.

**Needs — inputs.** The data the component needs, as a schema, with required and
optional fields. Most of it comes straight from the output schemas of the routes
the component calls. The developer maps each input to their app's data, or says
"I don't have this", which adds a column, a table or a setting to the plan.

**Gives — outputs.** What the component hands back to its host: events, state kept
in the URL, a refresh signal after a write. Each is wired up or ignored.

**Does — actions.** Every action with an effect, found from the code:

- writes, through `createAppClient(...).call("POST|PUT|PATCH|DELETE /...")`;
- the full effect of each write, from its route handler — table writes, connector
  calls (methods declared `mutates`), notifications, hooks fired, telemetry;
- navigation, from links and router calls, internal and external;
- downloads and clipboard copies.

For each one the card shows its trigger, what it changes, what it sends, who may
do it, and whether it is destructive or leaves the instance.

**Hidden rules.** Behavior inside a route handler that the UI doesn't show — in
the careers tracker, moving an application to "applied" for the first time
stamps an applied date. Each gets its own line and its own question.

**Parts.** Everything in the component that isn't an action: sections, columns,
badges, the empty state, the loading skeleton, and interactions such as filtering,
sorting and expanding. Kept by default; any can be removed.

Plus **Depends on** — tables, connectors, roles, platform capabilities — and the
**license verdict**: adapt or rebuild, and why.

## The decisions the developer makes

| Part | Choices | Default |
|---|---|---|
| Each action | **Same** — the equivalent in the target app, through one of its routes or a new one. **Different** — the control stays and does something else in the target app; the developer describes it, the agent offers matching routes, pages and connectors. **Remove** — the control is left out, not disabled, and anything only it needed goes too. | Recommended option first, with its cost ("Same: needs a `stage` column and a PATCH route"). No default for destructive actions, or for anything that leaves the instance (email, push, a write through a connector): those must be chosen. |
| Navigation into the source app | **Different** or **Remove** only (decision 11). | None. |
| Each hidden rule | Same / Different / Remove, asked on its own. | None. |
| Parts | A checklist; tick to remove. | All kept. |
| Each input | Map to the target's data, or add it. | The agent's best match, shown for confirmation. |
| Each output | Wire up or ignore. | Ignore. |
| Each kept action | Who in the target app may do it. Roles belong to each app, so the source's rule is restated in the target's terms. | The target app's existing rule for similar actions. |
| Keywords | Edit the agent's proposal. | The proposal. |

The card updates as choices are made: removing Edit drops its dialog and the
inputs only it used; Same for "Open posting" adds a `link` input.

## `/mixos remix`

```
/mixos remix <source-app>[:<widget-id|page-path>] <target-app> [notes]
```

The notes can name a part of a page: "the status chips above the table".
Modelled on `/mixos convert`: analyze, write the plan, stop; build after approval.

**Before anything.** Both apps are folders under `apps/`, and they are different
apps. Read the source's `license`, then pin the moment being remixed (decision 18):

- **With an install record** (`.registry.json`): its `commitSha`, and the
  catalogue listing and version it names. `modified` when the folder no longer
  matches the record's files hash — the check the generator already makes.
- **Without one:** `git log -1 --format=%H -- apps/<source>/`. `modified` when
  `git status --porcelain -- apps/<source>/` shows changes. A folder that was
  never committed has no commit: `commitSha` is null and `modified` is true.

The card shows the commit, and says so plainly when it is `modified`: the code
remixed isn't exactly the commit recorded.

**Analyze.**
1. Find the component's footprint: from the widget or page, through the routes it
   calls, their handlers, the `lib/server` code they use, the tables they touch
   (`context.db.table`), connectors, jobs, hooks and notifications.
2. Build the card. Detect any data the source reads from a third app through App
   Services; the remix maps that to the target's own data instead (decision 10).
3. Decide adapt or rebuild from the license (decisions 3, 4 and 16).
4. Ask the questions: one multiple-choice question per action and per hidden
   rule, with Different taking free text; the parts checklist; the input
   mapping; the keywords.
5. Write `apps/<target>/plans/YYYYMMDD_HHMM-remix-<source>-<component>.md`: the
   card, every decision, the input mapping, file-level changes, and a parity
   checklist built from the decisions — each kept or changed action, each hidden
   rule, each kept part is a row. **Stop for approval.**

**Build.** Following `/mixos app`:
- Code lands only in the target app. Imports are rewritten to the target's own
  files; the import allowlist already refuses anything else.
- An adapter sits between the target's data and the component's inputs, so the
  component keeps the shape it was abstracted with.
- New tables are new migrations in the target app's own schema, under the same
  migration allowlist as any other.
- **Adapting:** copied files keep the source's license notice at the top.
  **Rebuilding:** the target's code is written from the card. The agent reads the
  source to extract the card; that is not a clean room, and the plan says so. It
  avoids copying expression; it is not a legal clearance.
- Write the provenance entry (below), then verify: registry generation,
  typecheck, lint, tests, a browser pass over every row of the parity checklist.

## Provenance

The record of a remix, in the target app's `app.json`. It is committed with the
code, which is what "counts when merged" rests on, and it is the only thing
mixos.org reads.

```jsonc
"remixedFrom": [
  {
    "remixedAt": "2026-10-15",
    "source": {
      "app": "careers",
      // The moment remixed (decision 18): the install record's commit, or the
      // last git commit that touched apps/careers/. Null if never committed.
      "commitSha": "…40 hex…",
      "commitFrom": "install-record",          // or "git"
      "modified": false,
      // The catalogue listing, from the install record; null without one (decision 13).
      "registry": { "origin": "https://mixos.org", "slug": "careers", "version": "1.4.0" },
      // The component pointed at first, then what it drew on (decision 12).
      "anchors": ["page:/", "route:PATCH /applications/[id]", "route:POST /applications", "route:DELETE /applications/[id]"]
    },
    "summary": "Table of items with a status on each row, a status filter, and create, edit and delete",
    "keywords": ["status-table", "inline-status", "crud-dialogs"],
    "license": { "spdx": "MPL-2.0", "mode": "adapted" },   // or "rebuilt"
    "actions": { "change-status": "same", "edit": "different", "delete": "remove", "new": "same", "open-posting": "same", "go-to-library": "remove" },
    "hiddenRules": { "applied-date-stamp": "same" },
    "partsRemoved": [],
    "landedIn": ["pages/deals.tsx", "api/deals/[id]/route.ts", "api/deals/route.ts"]
  }
]
```

Validated by the manifest schema and the registry generator, for shape only:

- `keywords`: 2–5 after normalization, no duplicates.
- `anchors`: well formed (`widget:<id>`, `page:<path>`, `route:<METHOD> <path>`,
  `job:<name>`), and the first is a widget or a page.
- `commitSha`: 40 hex characters, or null with `modified` true; `commitFrom` is
  `install-record` or `git`; `remixedAt` is a date.
- `actions` and `hiddenRules` values are `same`, `different` or `remove`.
- `registry`, when present, names a catalogue origin, a slug and a version.

What held at the moment of the remix is checked once, by the agent, at the end of
the build — not by every later build, because the developer keeps changing the
code (decision 19): each `landedIn` file exists, and none links to a path under
`/apps/<source>/` (decision 11; the import allowlist already covers code, this
covers links).

**Entries are append-only.** The pre-commit hook and Danger refuse a change to an
existing entry in `remixedFrom`. Adding an entry is a new remix; deleting one
says the remix is gone from the app. Editing one would rewrite a moment.

The generator writes every app's entries to `src/generated/remix-index.ts`, which
the instance view reads.

### Keywords

Normalized the same way on the instance and on mixos.org:

1. lowercase; spaces and underscores become hyphens; other punctuation is dropped;
2. synonyms map to one term (`dnd` → `drag-and-drop`, `data-grid` → `table`);
3. words that describe nothing are dropped: feature, component, page, app, ui,
   data, view;
4. duplicates go.

No stemming: `status` must not become `statu`. The synonym list lives in one
platform module and is published with the mixos.org contract; mixos.org
re-normalizes when it aggregates, so a synonym added later merges old counts
too. The agent proposes one keyword per facet where it can — layout, interaction,
purpose — and keeps the kind of component (widget, page section) out of them.

## Where remixes are seen

**On the instance.** In the app details dialog under Administration → Apps:
"Remixed from" (this app's entries) and "Remixed into" (other local apps' entries
that name it). Read from `remix-index.ts`; no database, no tracking.

**On mixos.org** (the mixos.org repository). When a release of an app is
published, its `remixedFrom` entries are ingested into the mixos.org database
and kept for good (decision 21). One row per entry per remixing app, holding:

- the remixing listing, and the first and last of its releases the entry appeared in;
- the source listing, the source version and commit, and `modified`;
- `remixedAt`, the anchors, the keywords as written and as normalized, the
  license mode, and the action and hidden-rule decisions.

An entry is identified by its remixing app, source commit, first anchor and
`remixedAt`, so the same remix seen in ten releases is one row. A release that no
longer carries it closes the row; the row stays.

An entry counts toward a source listing when:

- its `registry.origin` is mixos.org, and the listing and version exist;
- it is in the latest published release of the remixing app (decision 17);
- the two apps don't share a publisher (decision 14).

**On the published app's page** (decision 22): one total — the number of apps that
remixed from it — with a breakdown by the source version they took it from
("1.4.0: 12 · 1.6.0: 8 · 1.7.0: 3"), each version showing its commit.

**In the creator's view**, per listing, the same total and:
- the breakdown by anchor — the page, widget or route — including anchors a later
  version no longer has, labelled with the last version that had them;
- the keywords people used for it;
- what survived: for each action and hidden rule, how often it was kept, changed
  or removed ("Change status kept in 20 of 23; Delete removed in 15");
- the history: remixes no longer in any latest release, and when each was dropped.

## Phases

1. The provenance format, its validation in the generator, the append-only check
   in the pre-commit hook and Danger, the keyword normalizer, and `/mixos remix`
   with its action file. Docs: `docs/apps/remix.md`.
2. The instance view in the app details dialog.
3. mixos.org: the remix table, ingest on publish, the counting rules, the
   version breakdown on the published app's page, the creator view.

Not planned: an in-product way to request a remix; author-declared remix points;
Different pointing at another app through App Services (decision 10); telling a
remixer that the source has changed (decision 20); updating a remix to a newer
source version, which is a new remix instead (decision 19).

## Verification, when built

- Remix the careers tracker into a scratch app. The card lists the six actions
  (change status, edit, delete, new, open posting, go to library), the
  applied-date hidden rule and the status filter, with no default offered for
  delete and only Different or Remove for "go to library".
- With every combination of Same, Different and Remove across those actions, the
  build passes, the parity checklist closes in a browser pass, and nothing the
  removed actions alone needed is left behind.
- The generator refuses an entry with one keyword or six, a malformed anchor, or
  a malformed commit. It accepts an entry whose `landedIn` files have since been
  renamed or deleted. The agent's end-of-build check refuses a missing landed file
  or one linking to `/apps/careers/`.
- The source commit: a catalogue install records its install record's commit; an
  edited install records it with `modified` true; a local app records the last
  commit touching its folder, and `modified` true with uncommitted changes; a
  never-committed folder records null.
- The pre-commit hook refuses a commit that edits an existing `remixedFrom` entry,
  and accepts one that adds or deletes an entry.
- Changing the source app after a remix changes nothing in the remixing app's
  entry or build.
- A source with no `license`, and one under GPL-3.0 into an MPL-2.0 target, are
  rebuilt rather than adapted, and the plan says why.
- Every landed file carries the credit comment, and the check refuses one
  without it.
- mixos.org, against fixture releases: a self-remix isn't counted; a remix
  carried by ten releases is one row; a release that drops an entry removes it
  from the total and keeps its row as history; the published app's page breaks
  the total down by source version; a remix of an anchor the latest version no
  longer has still counts; a later synonym merges two keywords' counts.

Two refinements made while building, both consequences of decision 19:

- **Keywords are checked in two places, differently.** The build checks only
  their shape — recorded normalized, 2 to 5, no exact repeats. Whether they
  survive the synonym list and the dropped words is checked once, by
  `scripts/remix.ts check`. An entry can't be edited, so judging old entries
  against a vocabulary that grows would fail an app's build with no fix.
- **"Nothing reaches back into the source" covers calls as well as links.** The
  one-time check looks for a link to `/apps/<source>`, a call to
  `/api/apps/<source>`, `createAppClient("<source>")`, `callAppRoute("<source>")`
  and an `@apps/<source>/` import in every landed file.

What building it settled:

- **The total counts apps, once each.** An app that took two parts, or one part
  from two versions, is one app. The version breakdown counts the apps that took
  from each version, so it can add up to more than the total; the page says so
  when it does.
- **The creator's view counts each abstraction.** A component's count is how many
  times it was remixed, and each of its actions shows how often it was kept,
  changed or removed. What it is typically called is its most used keywords,
  normalized with today's synonyms.
- **The remixing app is named only while it is published.** Once it is archived,
  its remix moves to the creator's history as "an app no longer listed".
- **Remixing apps that were never published are never shown**, the same gate the
  update check uses, so the creator's view can't reveal someone's draft.
- **A component is labelled with the newest version it was taken from**, not "the
  last version that had it": mixos.org keeps no file list per release, so it
  can't know when a page or route left the source. The count is unaffected: it is
  always against the version taken from.
- **Releases published before this record nothing** (`remixed_from` is null), so
  a remix counts from the remixing app's next release.
- **Matching is done when counting, by slug,** and only for the origin
  `https://mixos.org`. An instance pointed at another catalogue records its
  remixes, which are kept and never credited here.
