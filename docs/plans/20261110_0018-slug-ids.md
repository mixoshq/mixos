## Context

An extension's folder name is its slug, and the slug is its name everywhere: the app's URL, its
database schema and role, its grants, settings and API keys; a connector's credentials and its
OAuth redirect URI; the `data-theme` attribute a theme is compiled under. Two extensions with the
same slug can't be installed side by side. When a different one takes a slug an instance already
knows, the release step switches it off (`scripts/sync-app-registry.ts`,
`scripts/sync-identities.ts`). Plain names like `tasks`, `crm`, `slack` or `dark` will collide as
more people publish.

So every slug published from now on ends in a short random id: `sales-tracker-3f9a2c1b`.
Collisions can still happen, but two people would have to pick the same name *and* draw the same
32-bit id.

The manifests will change shape over time, and nothing in them says which shape they are. So
each one says so, with a `$schema` URL naming a published JSON Schema and its version.

## Decisions (locked with the owner)

### Slug ids

- **The id is part of the slug, everywhere.** The folder, the URL, the schema, the role, the
  `data-theme` value, the Registry listing and every manifest reference all carry it. It is not
  a display name: `app.json` `name`, `connector.json` `displayName` and `theme.json` `name` stay
  what people read.
- **Eight lowercase hex characters from a UUID, minted once.** The id is the first eight hex
  characters of `crypto.randomUUID()`. It is minted once and never changes or gets derived again.
  It is fixed by being recorded, not by being computed.
- **mixos.org mints it, the first time an extension is listed.** *Superseded by
  [`20261114_0947-registry-id.md`](20261114_0947-registry-id.md): the id is minted when the
  extension is created, written in its manifest as `registryId`, and mixos.org reads it.* This
  changes the first answer
  ("when it's scaffolded"). Extension repositories keep plain names, and the extension sits at
  the repository root, so nothing a publisher pushes carries a locally minted id. The Registry
  mints instead, on the website's Check and in the CLI's publish preview. A name that already
  ends in an id keeps it. The publisher then renames their own copy to match. For a connector,
  that means setting `name` in `connector.json` before its first release, because MixOS
  installs a connector only under that name. Built on mixos.org; see that section.
- **No URL redirects** from old slugs.
- **The existing core extensions are renamed. `_template*` folders are not.** `apps/wall-e`,
  `themes/mixos` and `themes/mixos-dark` each get an id minted locally by `npm run rename`. Every
  instance's data under the old slugs moves with them. Templates keep their names: the registry
  skips them.
- **Extension repositories keep their names.** `mixos-app-<name>` and the rest stay as they are.
  The id appears in the slug the extension is listed and installed under.

### Manifest versions (`$schema`)

- **A `$schema` URL in each file, and the schemas published on mixos.org.** For example,
  `"$schema": "https://mixos.org/schemas/app/v1.json"`. Editors that read `$schema` give
  completion and validation for free.
- **Required.** Scaffolding writes it, since the templates carry it, and the pre-commit stamp
  writes it where it is missing.
- **A version this MixOS doesn't read is refused.** Newer ones and older ones alike, with a
  message naming the MixOS release that reads it, or the migration that brings it forward.
- **It ships with slug ids, and mixos.org records it per release.**
- **It covers every JSON file MixOS reads from an extension:** `app.json`, `connector.json`,
  `theme.json`, `release-notes.json`, `.registry.json`, and the new `extension-renames.json`.

## Owner decisions (recommendations marked)

- **D1. The build accepts a slug without an id.** *Recommended. Superseded by
  [`20261114_0947-registry-id.md`](20261114_0947-registry-id.md): the build now requires one.* Every extension already on
  mixos.org, and every one in a MixOS user's own repository, has one. A local extension gets its
  id when it is first listed, so a build that refused slugs without an id would refuse everything
  being developed. *(Replaces the earlier pre-commit check, which assumed ids were minted at
  scaffold.)*
- **D2. A rename is recorded in a ledger at the repository root, not a manifest field.**
  *Recommended.* Manifests are written by publishers. A manifest field saying "I am what `x`
  was" would let any Registry release claim another extension's grants, API keys, credentials
  and tables. `extension-renames.json` is written only by `npm run rename`, in the operator's
  own checkout.
- **D4. A Registry-installed extension can't be renamed locally.** *Recommended: refuse.* Its slug
  is its publisher's.
- **D5. `/mixos upgrade` offers to rename a user's own extensions that have no id.**
  *Recommended: offer, one at a time, never automatically.* A connector with OAuth or webhooks
  needs its redirect URI re-registered in the provider's console, because the URI contains the
  name. The offer says so first.
- **D6. The fallback theme is the first by name with the id ignored.** *Recommended.* Otherwise
  the random id decides whether `mixos-<id>` or `mixos-dark-<id>` sorts first.
- **D7. A dark sibling gets its own id.** *Recommended:* `acme-dark-<new id>`.
- **D8. `release-notes.json` becomes an object.** *Agreed.* A top-level array has nowhere to put
  `$schema`, so the file becomes `{ "$schema", "notes": [...] }`. MixOS's own root
  `release-notes.json` changes too, so one reader handles both.
- **D9. One schema version per file, not one for the set.** *Agreed:
  `https://mixos.org/schemas/<file>/v<N>.json`.* A new `connector.json` shape doesn't force every
  theme to change.
- **D10. No extensions exist yet.** *Agreed.* v1 is the only version, nothing needs migrating,
  and there's no compatibility path. mixos.org requires `$schema` on every release from the
  start. A migration tool waits for a v2.

## Structure

### Slug ids in MixOS

- **`extension-renames.json`** at the root: `{ "$schema", "renames": [{ "kind", "from", "to",
  "date" }] }`, committed. The generator validates it: `to` is in the build, `from` is not, no
  `from` twice, no chains or cycles. It emits `src/generated/renames.ts`.
- **`npm run rename -- <kind>/<slug> [--to <new-slug>]`** (`scripts/rename.ts`):
  - Mints `<slug>-<id>`, or takes the slug mixos.org minted with `--to`, which must be `<slug>-<8 hex>`.
  - Moves the folder, adds the ledger entry, and rewrites the references it can recognise: the
    app's own `callAppRoute("<slug>"…)` and `createAppClient<"<slug>">`; a connector's `name`;
    other local apps' `consumes`, `listensTo`, `provides[].consumers`, `emits[].consumers`,
    `connectors`/`optionalConnectors` names, `mcp[].sources`, and the exact forms
    `context.connectors.<name>` and `context.connectors["<name>"]`.
  - Lists every other mention for a person to look at.
  - Never edits a `remixedFrom` entry (apps invariant 32).
  - Refuses a Registry install (D4), and hands back the commit.
- **The release-step carry-over**, `scripts/sync-renames.ts`. It runs before the app registry
  mirror in `scripts/release.ts` and in the `npm run migrate:apps` boot path, in one transaction
  under the release step's lock. For each entry whose `from` still holds data:
  - **App:** insert the `apps` row for `to` from `from`'s row. Repoint the foreign-key children
    (`user_app_grants`, `user_apps`, `app_passwords`, `app_mcp_tool_settings`,
    `dashboard_widgets`) and the tables keyed by slug alone (`app_settings`, `app_api_keys`,
    `_migrations`, `app_scheduled_jobs`, `app_job_runs`, `app_open_events`,
    `telemetry_events.source_slug` and `caller_app_slug`, `app_unlock_failures` keys). Run
    `array_replace` on the OAuth `granted_apps` arrays. Delete the old row, then rename the
    schema and the role with `ALTER SCHEMA` and `ALTER ROLE`.
  - **Connector:** `connector_configs`, `user_connector_oauth`, `connector_scope_status`,
    `connector_webhook_events`, `telemetry_events`, and the `connector.{identity,disabled,
    writable,replaced,missing}.<name>` settings.
  - **Theme:** the applied `theme` setting, and `theme.identity.<from>`.
  - If `to` already holds something, the entry is skipped and audited
    `<kind>.rename.skipped`. Otherwise each move is audited `<kind>.renamed`. Old audit rows keep
    the old slug. A second run is a no-op.
- **The three core extensions:** `npm run rename` on `apps/wall-e`, `themes/mixos` and
  `themes/mixos-dark`; `CORE_EXTENSIONS` takes the new slugs; the fallback order (D6) goes in the
  generator; and the hard-coded paths change (`src/components/onboarding/mixos-mark.tsx`,
  `src/lib/screenshots.ts`, `eslint-rules/no-low-contrast-token-pairs.mjs`, and the tests that
  name them).

### Manifest versions in MixOS

- **The schemas come from the Zod schemas MixOS already validates with**
  (`scripts/manifest-schemas.ts`), through `z.toJSONSchema`. They are written to
  `docs/schemas/<file>/v1.json` and committed. A test fails when they are stale. `$schema` is
  added to each Zod schema as a literal of the versions this MixOS reads, which today is v1.
- **The generator refuses** a file with no `$schema`, or with a URL it doesn't read. A newer
  version names the MixOS release that reads it. A URL that isn't one of MixOS's names the file
  and the field. A Registry install runs the same checks on its download.
- **Writers:** the templates carry `$schema`; install writes it into `.registry.json`;
  `scripts/stamp-updated.ts`, which the pre-commit hook runs, adds it to any extension file in
  the commit that lacks it, at the current version. The stamp never changes an existing value:
  moving a file to a new version is a migration (D10), not a stamp.
- **Upgrading MixOS:** `/mixos upgrade` stamps the user's own extensions, and turns their
  `release-notes.json` into an object (D8), before the build runs, so the upgrade doesn't break
  them. Installed extensions' `.registry.json` records gain `$schema` the same way.
- **What older MixOS sees:** its manifest schemas refuse keys they don't know (see
  mixos.org's `requires-mixos.ts`). So an extension that adds `$schema` builds only on the MixOS
  release that introduces it, or later. mixos.org therefore raises each release's floor to that
  version automatically.

### mixos.org

- **Built** (branch `feat/publish-form-slug-ids`):
  - `src/lib/registry/slug-id.ts`, with tests in `packages/cli/test/slug-id.test.ts`.
  - The website mints at Check and carries the id through Change and Save. The install name
    field is gone.
  - The CLI's publish preview mints, and the publish call sends the preview's slug back.
    `mixos check` shows `apps/<name>-<id>`, and `mixos publish` says when the local folder's
    name differs from the listing's.
  - Reserved names are checked on the base. At a repository's root the base comes from the
    repository name less `mixos-<kind>-`.
  - A connector whose `name` lacks an id is draft-only until it matches.
  - The publish form's layout changes, the shared select caret, and the docs.
- **Built with it** (same branch, PR 2):
  - `npm run sync:docs` copies core's `docs/schemas/` to `public/schemas/` and the index to
    `src/data/manifest-schemas.json`. `/schemas/` is exempt from the kill switch.
  - `manifest-schema.ts`: every release must name a schema this site lists, for its own file,
    that a released MixOS reads. Its floor is raised to that release.
  - `releases.manifest_schema` (migration 0020) records it, locked like the commit.
  - `slug-references.ts`: an app release whose code names another slug is refused.
  - `is_valid_slug` refuses a reserved name with an id (migration 0021). The site's own format
    check does the same.
  - `release-check.ts` holds all of it, run by the website's two publish pages and the CLI's
    endpoint before writing, and again in `recordRelease`.
  - `mixos check` warns about `$schema`.
  - Not done: returning the schema from the resolve API.
