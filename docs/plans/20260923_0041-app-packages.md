# App packages: declared libraries and a closed import graph

**Status:** proposed; partly superseded by [`20261007_0153-app-import-allowlist.md`](20261007_0153-app-import-allowlist.md)
**Scope:** platform — `src/lib/apps/`, `scripts/`, `src/lib/repository/install.ts`, `eslint-rules/`, `eslint.config.mjs`, docs, the `/mixos` skill

> **Partly superseded.** The import half of this plan was built as the app
> import allowlist, [`20261007_0153-app-import-allowlist.md`](20261007_0153-app-import-allowlist.md):
> Phase 1's import scan (`scanAppImports` in item 2, and items 4 and 5) and
> decisions 9 and 13, with the policy at `src/lib/apps/import-policy.mjs` in
> place of `package-policy.mjs`. It also brought forward the generator's refusal
> of `node_modules/` and `package.json` from decision 1, and it allows no Node
> built-ins, where decision 8 proposed four. What stays here: decision 1's
> installer preflight and lockfiles, decision 10 (refusing JS-family files), and
> Phase 2 (`packages`), which adds entries to the same policy.

## Context

An app that wants a library has no documented way to get one — and an
undocumented way that works too well: an app file can import anything in the
instance's root `node_modules`. Nothing declares it, nothing bounds it, and
nothing tells the admin installing the app. Between them, apps import three
packages today (`zod`, `react`, `next/link`),
so the problem is not yet in the code. It is in what the code is allowed to do.

The app-tier `no-restricted-imports` blocks in `eslint.config.mjs` are a denylist
of `@/` spellings. Each row below was run against the current config with
`npx eslint --stdin --stdin-filename <path>`, and every row but the first passes
with zero errors:

| Import, from an app file | What it reaches | Lint today |
|---|---|---|
| `@/lib/db` in `api/**/route.ts` | the raw DB client (service role, bypasses RLS) | error |
| `../../../../src/lib/db/client` in the same file | the same module | **passes** |
| `postgres`, `next-auth` in `lib/server/**` | a DB driver; the session | **passes** |
| `node:fs` → `readFileSync(".env.local")` | every secret the `process.env` ban protects | **passes** |
| `child_process`, `node:https` | a shell; a network client the `fetch` ban never sees | **passes** |
| `@apps/other-app/lib/server/db` in wall-e's `api/**` | another app's server tier, around App Services consent | **passes** |
| `process.env` + `fetch` in a **`.js`** file | the same code that fails as `.ts`, with two errors | **passes** |

Three structural facts make this worse than a handful of missed patterns.

1. **Lint does not run where extension code arrives.** `next build` stopped
   linting in Next 16 (`node_modules/next/dist/docs/01-app/02-guides/upgrading/version-16.md:1084`).
   ESLint runs in exactly one place, this repository's CI
   (`.github/workflows/ci.yml:53`). The installer's only validation is the
   registry generator (step 9 in §31 of `docs/security-architecture.md`), and a dev
   instance's `predev` runs the generator too. Now that
   [`20260922_2320-extension-dev-instances.md`](20260922_2320-extension-dev-instances.md)
   moves extensions into their own repositories, most app code will never pass
   through this repository's CI. An import rule that lives only in ESLint is
   advisory for exactly the code it most needs to govern.

2. **A nested `node_modules` wins.** Resolution walks up from the importing
   file's real path. The dev-instances plan hit this directly: `zod` resolved
   against a sibling repo's absent `node_modules`. So
   `apps/<slug>/node_modules/<pkg>` shadows the instance's copy of any package,
   `react` and `zod` included. Nothing refuses it. The installer rejects symlinks,
   traversal and oversize trees, but not `node_modules/` or `package.json`
   (`fetch-source.ts` filters by subpath only), and the root `.gitignore` entry
   is anchored (`/node_modules`). An extension that is its own git repository
   invites someone to run `npm install` inside it. Even with no bad intent, that
   breaks things: two copies of React is the classic broken-hooks failure.

3. **JS-family files are outside every app rule.** Every app block in
   `eslint.config.mjs` matches `apps/**/*.{ts,tsx}`, while `tsconfig.json` sets
   `allowJs: true`. A `.js`, `.mjs`, `.cjs`, `.jsx`, `.mts` or `.cts` file is
   importable from app code, yet no containment rule lints it. So as soon as bare
   imports are fenced, "copy the library into `lib/vendor/`" becomes an unreviewed
   way around every rule above.

**Intended outcome:** an app's import graph is closed and declared. An app
file can load only four kinds of module: its own source, a platform module under
`@/`, a core package, or a package its manifest declares from a platform-vetted
allowlist. The generator enforces this on every path by which code enters an
instance, and ESLint gives the same answer in the editor.

## Decisions

| # | Decision | Why |
|---|---|---|
| 1 | **No per-app `package.json`, `node_modules/` or lockfile.** The installer refuses them before writing anything, and the generator refuses them in a tree that arrived any other way. | One manifest (`app.json`), one `node_modules`, one lockfile. A per-app install runs third-party install scripts on the host and pulls in a transitive tree that no manifest names. |
| 2 | **Manifest field `packages: string[]`**: names only, no versions. | Not `dependencies`, because that word carries npm's meaning (versions, installs), which this field deliberately lacks. |
| 3 | **The platform owns every version.** The allowlist names packages; root `package.json` pins them. | Apps cannot disagree about a version, so there is nothing to dedupe or resolve. The cost is that a major bump moves every app that declared the package at once, so it is an OS change and gets the same review as a token removal (`OS-UPDATES.md`). |
| 4 | **The allowlist criterion: pure computation is allowlisted; UI and I/O are wrapped; infrastructure is never available.** | See the triage below. A library that renders its own UI sidesteps the primitives and the contrast rules: a chart library picks its own series colours, and the class-literal contrast rule cannot see them. A library that does I/O sidesteps `context.http`, `context.env` and `context.db`. |
| 5 | **Seed the allowlist with `cronstrue`.** | It is already a runtime dependency (`src/components/admin/scheduled-jobs-list.tsx`) and is pure: a cron string in, a sentence out. It proves the whole path without adding any new supply chain. |
| 6 | **Core packages need no declaration:** `react`, `zod`, `lucide-react`, `next/link`, `next/navigation`, `next/font/google`, `next/font/local`. | This is exactly what apps import today plus what the app docs teach, so no existing app needs a manifest change. |
| 7 | **Type-only imports are exempt** from the package and cross-app rules. | They are erased at build, and a type cannot execute. The scoped-DB rule already uses the same reasoning, and it keeps `import type … from "@apps/file-library/services/types"` in `docs/apps/app-services.md` working. |
| 8 | **Node built-ins are default-deny.** The server tier may import `node:crypto`, `node:buffer`, `node:url` and `node:util`. `fs` and `node:fs` normalize to one name. | `fs`, `child_process`, `net`, `http(s)`, `dns`, `worker_threads`, `vm` and the rest are exactly the capabilities `context.*` exists to mediate. |
| 9 | **Relative imports stay inside `apps/<slug>/`.** Platform code is reached only via `@/`. `@apps/<own-slug>` is fine; `@apps/<other>` is type-only. No `require()`, and no `import()` with a non-literal argument. | A denylist of spellings only means something if each module has one spelling. No app imports `@apps/*` at runtime today. |
| 10 | **An app's source is TypeScript.** Any `.js/.jsx/.mjs/.cjs/.mts/.cts` file in an app tree is refused. | None exist in `apps/` today. Vendored code has to be readable, linted source like the rest of the app. |
| 11 | **Vendoring small, pure TypeScript is allowed.** It is app source, under every rule. Keep its license notice, and vendor source, not a build artifact. | This is the honest path for a 40-line utility that doesn't justify an allowlist entry. |
| 12 | **The generator is the enforcement point, and ESLint gives feedback.** Both read one policy module. | The generator runs on every path: `predev`, `prebuild` and install step 9. Two implementations of one policy would drift. |
| 13 | **The existing `@/` denials move into the policy module** with the same patterns, tiers and messages. A new rule replaces the three app `no-restricted-imports` blocks. | They have the same install-path gap, and the raw DB client is more dangerous than any npm package. Keeping two lists would bring back the drift that decision 12 prevents. |

### Triage of what the platform already ships

| Package | Platform uses it for | For apps |
|---|---|---|
| `react`, `zod`, `lucide-react`, `next/link`, `next/navigation`, `next/font/*` | everything | **Core** |
| `cronstrue` | scheduled-jobs list | **Allowlisted** (seed) |
| `clsx`, `tailwind-merge` | `cn()` in `src/lib/utils.ts:8` | **Already wrapped.** Import `cn` from `@/lib/utils` |
| `react-markdown`, `remark-gfm` | guide tabs | **Wrap.** It renders HTML, and sanitization belongs to the `raw-html` escape |
| `mermaid` | guide diagrams (`src/components/guide-mermaid.tsx`) | **Wrap.** It renders UI |
| `croner` | `src/lib/apps/cron.ts` | **Never.** It can schedule its own timers, which invariant 17 forbids |
| `react-grid-layout` | the dashboard grid | **Never.** It is platform chrome |
| `postgres`, `@supabase/supabase-js` | the database | **Never.** These are the raw client and the service role |
| `next-auth`, `bcryptjs` | sessions and passwords | **Never** |
| `web-push` | push delivery | **Never.** Use `context.notifications` |
| any other `next/*` (`next/headers`, `next/server`, …) | the framework | **Never by default.** Cookies, the session and responses belong to the platform |

An allowlist request is a PR against the policy module that answers these
questions. Does the package do I/O (network, filesystem, environment,
processes, workers, timers)? Does it render UI? Does it mutate globals? Does it
ship install scripts (`npm view <pkg> scripts`)? How deep is its transitive
tree? A yes to any of the first four means wrap or never, not an allowlist
entry.

## Constraints (build-enforced)

| Rule | Enforced by |
|---|---|
| Every `packages` entry is on the allowlist | schema, install preflight |
| A `packages` entry is not core, is not duplicated, and is actually imported | generator |
| A bare import is core or declared | generator, lint |
| A never-available package or a denied built-in cannot be imported, declared or not | generator, lint |
| A `tier: "server"` package or built-in is imported only from `api/`, `lib/server/`, `services/`, `mcp/`, `jobs/` or `sync/` | generator, lint |
| Relative imports resolve inside `apps/<slug>/`; `@apps/<other>` is type-only; no `require()`; no `import()` with a non-literal argument | generator, lint |
| The existing `@/` denials: raw DB client, connectors in the client tier, context builder, scoped-DB factories | generator, lint (moved, not changed) |
| No `node_modules/`, `package.json` or lockfile anywhere in the app tree | install preflight, generator |
| No JS-family source files in the app tree | install preflight, generator |
| Every allowlist entry is in root `package.json` `dependencies` | generator (a platform self-check) |

Every failure names the file, the line, the specifier and the fix. The generator
reports all of an app's violations before aborting, not just the first.

## File-level changes

### Phase 1: close the holes (no manifest change)

This phase ships on its own and is the security half of the plan. With the
allowlist empty, "core or declared" means core only, which covers everything any
app imports today.

1. **`src/lib/apps/package-policy.mjs`** (new) holds the whole policy and has no
   dependencies. It contains `CORE`; `ALLOWLIST` (name → `{ tier, reason }`,
   empty in this phase); `NEVER` (name → reason); the permitted built-ins; the
   server-tier directories; the `@/` denials moved from `eslint.config.mjs`, with
   their messages and comments; and
   `classifyImport({ specifier, typeOnly, importedNames, file, appSlug, declared })`.
   It is plain `.mjs` with JSDoc types so that `eslint.config.mjs` can load it
   under plain Node, the same reason the contrast rule reads platform data from
   disk. TypeScript consumers import it through `allowJs`. `packageName()` is
   scope-aware (`@scope/pkg/sub` → `@scope/pkg`) and strips `node:`.

2. **`scripts/generate-project-registry.ts`**
   - `validateAppTree(slug, dir)` refuses `node_modules/`, `package.json`,
     lockfiles (`package-lock.json`, `npm-shrinkwrap.json`, `yarn.lock`,
     `pnpm-lock.yaml`, `bun.lock`, `bun.lockb`) and JS-family files.
   - `scanAppImports(slug, dir, declared)` parses every `.ts`/`.tsx` file with
     the TypeScript compiler API, syntax only (`ts.createSourceFile`).
     `typescript` is already a devDependency, and the generator already runs
     only where dev tooling is installed (it runs through `tsx`). The scan
     visits import and export-from declarations, `import()` and `require()`
     calls, and `import x = require()`. It records whether each declaration and
     each specifier is type-only, and it resolves relative specifiers against
     the importing file to check containment. It collects every violation, then
     aborts.

3. **`src/lib/repository/install.ts`**: `preflight()` gains item 2's tree
   checks (`node_modules/`, `package.json`, lockfiles, JS-family files), failing
   as `invalid-package`. It runs on the in-memory tree, before step 7 writes
   anything.

4. **`eslint-rules/app-imports.mjs`** (new) is the editor half and uses the same
   policy module. It takes the tier and the slug from the file path, and the
   declared packages from `apps/<slug>/app.json`.

5. **`eslint.config.mjs`** registers `mos-apps/app-imports` for app files. It
   removes the three app `no-restricted-imports` blocks, whose content now lives
   in the policy module. It also widens the globs of the app containment blocks
   from `{ts,tsx}` to include `js,jsx,mjs,cjs,mts,cts`, so the editor flags a
   file before the generator refuses it.

6. **`docs/security-architecture.md`**: step 6 of §31 gains the tree refusals.
   §3.3 states where import rules are enforced (the generator, on every path)
   and where lint runs (this repository's CI and the editor).

### Phase 2: declared packages

7. **`scripts/manifest-schemas.ts`** adds an optional
   `packages: z.array(z.string())` to `RawAppManifestSchema`, refined against the
   policy. An unknown name fails with "not a package MixOS provides to apps". A
   `NEVER` name fails with that entry's own reason, because it is a different
   problem with a different fix.

8. **`src/lib/apps/types.ts`**: add `packages: string[]` to `AppManifest`,
   default `[]`, carried through by the generator.

9. **`src/lib/apps/package-policy.mjs`**: `ALLOWLIST` gains
   `cronstrue: { tier: "any", reason: … }`.

10. **Generator**: a declared package that is never imported is an error, and
    so is a declared core package. Add the allowlist self-check against root
    `dependencies`, and emit `packages` into the registry.

11. **`src/lib/repository/install.ts`**: preflight checks each declared package
    against *this instance's* allowlist and fails as `incompatible`. That is the
    existing code for "a release that needs platform features this build does
    not have", and it has no override for the same reason. `packages` joins
    `egress`, `escapes` and `connectors` in the comment at
    `src/lib/repository/types.ts:161` as manifest-enforced truth.

12. **`src/components/admin/app-details-dialog.tsx`** lists declared packages.
    `docs/apps/architecture.md` says `escapes` are "shown on the app's admin
    page", but nothing under `src/` renders them, so fix that in the same place.

13. **Docs.**
    - `apps/AGENTS.md`: add invariant 30.
    - `docs/apps/architecture.md`: add a `packages` row to the field reference
      and a "Using a library" section (core → declared → wrapped → vendored
      TS → request). Rewrite line 181 ("Any import that works in runtime TS
      works here"), which stops being true.
    - `WHATS-NEW.md`: add an entry.

14. **`/mixos` skill.**
    - `actions/app.md`: explain how to add a library, and say never to run
      `npm install` inside an extension.
    - `actions/convert.md`: map every dependency in the source's `package.json`
      to one of core, allowlisted, platform primitive, connector or unavailable.
      Record the unavailable ones in the conversion plan as decisions for the
      user.

`apps/_template/app.json` gets no `packages` key, so a scaffolded app builds
green, as with `screenshots`.

## Verification

### Phase 1

1. **Every row of the Context table fails at both layers**: through
   `npx eslint --stdin --stdin-filename <path>` with the same inputs, and
   through the generator with the same content as a scratch file in
   `apps/wall-e/`, removed afterwards. Each generator failure names the file,
   the line and the specifier.
2. **Existing denials are unchanged.** `@/lib/db` in a route,
   `@connectors/<x>` in a widget and a named `createScopedClient` import produce
   the same errors with the same messages. Still allowed:
   `import type { ScopedClient }`, and `import type` from
   `@apps/<other>/services/types`.
3. **Shadowing is demonstrated, then refused.** Before the change, a stub
   `apps/wall-e/node_modules/zod/` is what wall-e's routes load under
   `npm run dev`, which proves the vector is real. After the change, the
   generator refuses the tree.
4. **Install path, in `mixos-test`.** Crafted extensions carrying
   `node_modules/`, a `package.json` or a `.js` file each fail at preflight as
   `invalid-package`, and `.installing-<slug>` never appears on disk.
5. **Nothing regresses.** `npm run registry` is clean for `wall-e`,
   and `npm run typecheck`, `npm run lint` and `npm run build` are clean.

### Phase 2

6. **Positive path.** In a scratch change to wall-e, declare `cronstrue` and
   import it in a route. The generator passes, the registry carries
   `packages: ["cronstrue"]`, and the admin dialog lists it.
7. **Each failure produces its own message:** importing without declaring;
   declaring without importing; declaring `react` (core); declaring `left-pad`
   (not provided); declaring `postgres` (never, with the reason); importing
   `node:crypto` from a widget (tier).
8. **Self-check.** An allowlist entry that is missing from root `dependencies`
   fails the generator.
9. **Install preflight.** In `mixos-test`, an extension declaring a package this
   instance does not provide fails as `incompatible`, before anything is
   written.

## Out of scope

- **Connectors.** Their demand is for SDKs, which do network I/O by definition,
  so criterion 4 doesn't transfer. They need a separate plan.
- **Publishing `packages` to mixos.org** so the register dialog can show it
  before install. The field lives in `app.json`, so the catalogue can read it
  whenever it is ready.
- **The platform wrappers themselves**, such as a chart primitive or a markdown
  primitive. Each needs its own plan; this one only decides that UI libraries
  arrive that way.
- **Per-app bundling**, where each app's vendored dependencies are built into
  an isolated chunk. This is the escape hatch if allowlist churn becomes the
  bottleneck, and not before, because it reopens the supply-chain surface this
  plan closes.

## Adjacent gaps found, not closed here

1. **The non-import containment rules have the same install-path gap.** The
   `process.env` and raw `fetch` bans, the raw-element bans and the contrast rule
   are ESLint-only too. They are therefore advisory for installed extensions and
   for extension repos in a dev instance. The comment at
   `.github/workflows/ci.yml:43-50` says lint is "what makes that sentence
   true", which holds only for pull requests to this repository. The fix has the
   same shape: run app-scoped lint at install step 9 and in `predev`, or extend
   the generator's scan.
2. **`globalThis.fetch(…)` passes the fetch ban** (verified), because
   `no-restricted-globals` matches only the bare identifier. Add
   `no-restricted-properties` entries for `globalThis`, `window` and `self`.

## Open questions

1. **Test tooling for extension repositories** is the one legitimate reason an
   extension might want a `package.json`. The preferred answer is that the
   instance provides a test runner at the root, which keeps one `node_modules`.
   Decision 1 stands until this is settled.
2. **Minimum-version signalling.** Should each allowlist entry record the MixOS
   version that introduced it? The `incompatible` message could then say "needs
   MixOS ≥ X", and publishers would know what to put in `requiresMixOS`.
3. **Danger check.** When `ALLOWLIST` changes, should Danger post decision 4's
   questions as a review checklist?
